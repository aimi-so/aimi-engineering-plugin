# Aimi Engineering Plugin - Development Guidelines

## Versioning Requirements

**Every change to this plugin MUST include:**

1. **Bump version** in `.claude-plugin/plugin.json` (follow semver)
   - MAJOR: Breaking changes to command syntax or output format
   - MINOR: New commands, skills, or features
   - PATCH: Bug fixes, documentation updates

2. **Update CHANGELOG.md** with the change description
   - Follow [Keep a Changelog](https://keepachangelog.com/) format
   - Categories: Added, Changed, Fixed, Removed, Security

3. **Update README.md** component counts if adding/removing components

4. **Update marketplace.json** version to match plugin.json

## Security Requirements

### Input Validation (CRITICAL)

1. **branchName validation** - Must match `^[a-zA-Z0-9][a-zA-Z0-9/_-]*$`
   - Prevents command injection in git operations
   - Reject invalid names before any git command

2. **Story content sanitization** - Before prompt interpolation:
   - Strip newlines, markdown headers, code fences
   - Validate field lengths (title: 200, description: 500, criterion: 5000)
   - Reject suspicious content ("ignore previous instructions", shell syntax)

3. **Bash permissions** - Use specific prefixes in allowed-tools:
   - `Bash(git:*), Bash(npm:*), Bash(bun:*), Bash(tsc:*)` etc.
   - Never use unrestricted `Bash` in commands that spawn Task agents

## Hook Conventions

- Hooks emitting hookSpecificOutput must gate on CLAUDECODE env var when their output schema is Claude Code-specific.

### Staging-file guard

`hooks/guard-runtime-state.py` — the `Write|Edit` PreToolUse hook registered in `hooks/hooks.json` — refuses a hand edit of a **staged story file**: a target whose last four path components are `.aimi/.tasks-staging/<run>/NN-*.json`. The rule is judged from the resolved target's components alone, never from the working directory, so a run directory under a worktree's own `.aimi/` is treated like the main checkout's.

- **Denied:** any tool other than `Write` (so `Edit`, by anyone), a `Write` over an existing story by the main session, and a `Write` over an existing story that has a validation stamp beside it, whoever the caller is. The denial is the structured `permissionDecision: deny` at exit 0, like the hook's other blocks that point at a verb, and its message names both sanctioned routes: `apply-audit-patches` (see its section under Story Lifecycle Subcommands), or delete the file and re-run the expander.
- **Allowed:** a `Write` that creates a file that does not yet exist (that is the story expander's own output); a `Write` over an existing story **by a subagent while no stamp exists beside it** (the expander fixing the validation defect it was re-spawned for); the sidecars `outline.json`, `metadata.json`, `audit-result.json` and any `*-outline.json` (the name rule is the one `story_merge.py`'s `is_sidecar` applies in the other direction, so the hook and the merge agree on what a story is); and an `NN-*.json` outside a `.tasks-staging/` run directory.
- **The validation stamp.** `NN-<slug>.json.validated` beside a staged story is the orchestrator's record that the story passed Schema Validation steps 2 and 2b (`commands/references/plan/phase-3d-validate-retry.md`); it holds the sha256 hex of the story file. The hook compares nothing inside it: the file's existence alone closes the story to every Write and Edit, which fails closed, and the digest is there so a later reader can tell whether the file changed after validation (for example after `apply-audit-patches` rewrote it). The stamp name never ends in `.json`, so `story_merge.staging_files` (which globs `*.json`) and `audit_patches.staged_idx_map` (which full-matches `...\.json`) never read it as a story, and `outline-shift` renames it and deletes it together with its story file. The hook denies **any subagent Write or Edit of a stamp** in every state, and leaves the main session free to write one. The stamp name is never judged as a story or a sidecar.
- **The subagent signal.** `is_subagent_write(payload)` is true when the hook payload carries a non-empty `agent_type` or `agent_id`; the main session carries neither. It reads the dict the hook already reads `tool_name` from. `staging_stamp(path)` derives the stamp path from a story path.
- **The expander context directory.** `<RUN_DIR>/context/` holds the shared blocks every expander of a run reads (`commands/references/plan/phase-3d-context-files.md`: the outline, the consolidated research, the resolved decisions, the specs and the other blocks of its table), written once by the orchestrator with the Write tool. The hook denies **any subagent Write or Edit at or below a `context` directory two components under `.aimi/.tasks-staging/`** (`_is_expander_context_dir`, judged from path components alone like the story rule, so a worktree-nested run directory is treated like the main checkout's), and leaves the main session free to write there. The reason is that one expander able to rewrite a file its siblings read would change what they are told. `story-merge` and `apply-audit-patches` never list the directory as a story, and `story-merge` removes it together with the run directory. The rule inherits the guard's limits below: Bash, OpenCode and `AIMI_RUNTIME_STATE_GUARD=off` walk past it.
- **Why:** once a story is expanded and audited it is consistent with its siblings, and a hand edit drifts it out of that consistency while leaving the audit result describing text that no longer exists. The sanctioned edit path validates, sanitizes and writes atomically.
- **It is a guard rail against accidental edits, not a security boundary, and the hook's own docstring says so.** What walks straight past it: a Bash command (`sed -i`, `jq … > file`, a redirect) because the hook is registered on `Write|Edit` only; an OpenCode session, because `install.sh` wires no hooks; `AIMI_RUNTIME_STATE_GUARD=off`, which disables every block in the file; a staging directory that is not under `.aimi/.tasks-staging/`; the `exists()` check, which is not atomic with the write that follows it; and a subagent overwriting a **sibling's** unstamped story, because the hook knows that a subagent is calling but not which story it was handed (a known bypass beside Bash). OpenCode wires no hooks, so there the stamp is instruction-only. Do not build a guarantee on it. The gate that makes a skipped audit visible is the one in `story-merge`, not this hook.
- **Tests:** the `test_staged_story_*` cases in `hooks/tests/test_runtime_state_guards.py` cover a new file, an `Edit`, a `Write` over an existing file (and that the reason names both routes), the sidecars, a same-named file outside `.tasks-staging/`, a worktree-nested run directory and the env bypass. The `test_stamp_*`, `test_is_subagent_write_*` and `test_staged_*subagent*` cases beside them cover the subagent signal, the unstamped subagent rewrite, the stamped and main-session denials, the stamp deny for subagents, the main session's free stamp write, and the stamp name never being judged as a story. The `test_expander_context_*` cases cover the context directory: a subagent's Write and Edit denied, `agent_id` alone enough, the main session allowed, lookalike paths outside a staging run allowed, a worktree-nested run directory, the component-only predicate and the env bypass. The stamp is also pinned from the other side: `test_outline_shift_stamp_*` in `scripts/tests/test_outline_contract.py` (rename, delete, no orphan) and the stamp-ignored cases in `test_story_merge.py` and `test_audit_patches.py`.

## Command Conventions

- Use `aimi:` prefix for all commands — always show `/aimi:plan`, `/aimi:execute`, etc. in output, NEVER the fully-qualified `/aimi-engineering:plan` form
- Use `disable-model-invocation: true` for side-effect commands
- Wrapper commands should pass `$ARGUMENTS` to wrapped commands
- Document allowed-tools in frontmatter with specific Bash prefixes
- **Agents declare their tools with the `tools` key; commands and skills keep `allowed-tools`.** Claude Code reads `tools` (a comma string) on an agent file and ignores `allowed-tools` there, so a list under the old key restricted nothing. The list is an accident guard and not a sandbox: an agent that lists Bash can still write, because a shell redirect needs no Write tool. A tool name the host does not have is dropped silently; Grep and Glob are absent on some Claude Code builds, which is why every read-only agent that lists them also lists Bash, so search keeps working. `scripts/tests/test_agent_tools.py` pins each agent's list (`TABLE`), requires that every agent declaring `tools` is in the table, and reads the agent files as text. An agent that is in no table row declares nothing and keeps every tool.
- Validate inputs before passing to external commands
- See `commands/references/user-communication.md` for the wording/tone rules governing text written to the human reader (completion reports, chat explanations, `AskUserQuestion` prompts); this file references them (no duplication)
- `commands/` (including `commands/references/`) is subject to a size discipline, the same as `SKILL.md` below — but the discipline that keeps a command small is a rule about *where content belongs*, not a line count to trim toward. `commands/references/context-budget.md` is its normative home: a deterministic procedure belongs in an `aimi-cli.sh` verb, a rare conditional judgment in a lazily-read `commands/references/` file, an always-needed "does this apply?" check inline in the parent. It is not restated here, and the enforceable per-file budget that backs it arrives with `scripts/test-command-size.sh`
- Before adding a new validation gate — a verb that returns a verdict, a validator warning, a criterion a story must satisfy — answer the question in `commands/references/context-budget.md` § *The Question Every New Gate Must Answer* first; that same section is where the three fields sharing the word `verification` are told apart. Neither is restated here, for the reason this file already gives twice about one rule living in two places

## Agent Model Categories

A namespaced agent (`subagent_type="aimi-engineering:<category>:<name>"`) runs on the model configured for the category named by its directory under `agents/` (`research`, `review`, `design`, `workflow`); the spawn site reads it from `AGENT_MODELS` and omits the `model:` line when the value is `inherit`. `commands/references/cli-path-resolution.md` § Applying the resolved model to a Task call is the rule's home and is not restated here. The category is therefore a property of where the agent file lives, and moving a file changes which model it runs on.

- **`aimi-cross-story-auditor` runs on the review model category.** It lives at `agents/review/aimi-cross-story-auditor.md` and Phase 3d.5 (`commands/references/plan/phase-3d5-audit-spawn.md`) spawns it as `aimi-engineering:review:aimi-cross-story-auditor` with `AGENT_MODELS.review`. It was `aimi-engineering:workflow:` with `AGENT_MODELS.workflow` before, so a user who configured those two categories differently now gets a different model for the audit. The auditor reads a plan and judges it, which is what the review category is for. `install.sh` translates it as `aimi-cross-story-auditor` by its `agents/*/*.md` glob, so the OpenCode name did not change.
- **Its size budget is exact.** The agent file is over the shared 16384-byte ceiling, so `scripts/command-size-baseline.txt` carries a line for `agents/review/aimi-cross-story-auditor.md` at the file's own size (20048 bytes as of release 1.155.0, after the auditor was changed to read its corpus from `RUN_DIR`; it still has nine concerns; re-measure with `wc -c`). The ratchet fails in both directions, so an edit that grows or shrinks the file changes that number in the same commit.

## Artifact Language Ratchet

`commands/references/user-communication.md` § Artifact Language Rule states the rule once: an artifact under `.aimi/` is a plugin-owned artifact and is written in English, whatever language the person, the target project, or a quoted spec is in. Stating it once does not reach a writer added after the fact, so `scripts/test-artifact-language.sh` derives the writer set from the tree on every run and refuses to be green while any derived candidate carries neither the anchor nor a reasoned exemption — see root `CLAUDE.md` § Testing for when to run it.

**The candidate set is the union of two predicate arms over `command_block_files()`'s corpus, never a hand-written list.** Arm (a): the file contains a `.aimi/<root>/` (or `~/.aimi/<root>/`) path literal whose `<root>` is not declared `non-artifact-root` in `scripts/artifact-language-baseline.txt`. Arm (b): the file's frontmatter `tools:` line (an agent) or `allowed-tools:` line (a command or skill) names `Write`; both keys are read, because the two kinds of file spell it differently. Neither arm alone is sufficient — arm (a) misses a writer whose output path arrives from its caller with no `.aimi/` literal of its own (a prototype-author agent told `outputPath`), and arm (b) misses a writer with no `allowed-tools` key at all (a research agent whose frontmatter is name/description/model only) — so the candidate set is their union, and the suite's own discrimination fixture proves both arms load-bearing rather than assumed to be.

**A candidate is anchored in one of two forms, matched against declared literals only, never the bare word "language".** Form R (reference): the file contains the literal path to the rule's home file. Form S (statement): the file carries a markdown heading, at any level, whose text is EXACTLY the declared section literal (`## Artifact Language Rule`), matched as a whole line, never a substring. A writer whose own "what you do NOT do" section forbids opening an arbitrary reference file at run time states the rule inline (Form S, e.g. `agents/workflow/aimi-story-expander.md`); a writer free to read at run time cites it instead (Form R). Both literals are declared exactly once, in `artifact-language-baseline.txt`'s `anchor-ref`/`anchor-section` lines, and the suite cross-checks them against the rule's own home on every run — a renamed or moved rule breaks in that one visible place rather than silently un-anchoring every writer at once. Measured before this ratchet existed: 7 of the corpus's 25 candidates already contained the bare word "language" in ordinary prose, 5 of them genuine writers — a word-level match would have reported them anchored for the wrong reason, over exactly the files that matter most.

**`artifact-language-baseline.txt` carries four kinds of tab-separated line** — `anchor-ref`, `anchor-section` (both declared once, above), `non-artifact-root` (a `.aimi/` root excluded from arm (a); absence means IN SCOPE, so a new artifact directory is caught rather than walked past), and `exempt` (a candidate that reads rather than authors a `.aimi/` artifact, or that authors into the target project's own source instead). `non-artifact-root` and `exempt` both REQUIRE a `#`-prefixed one-line reason, the same per-line-reason shape `command-blocks-baseline.txt` already uses — and the same file is a ratchet in **both** directions, the rule `command-size-baseline.txt` states for its own byte budgets: an `exempt` entry naming a file that no longer matches the candidate predicate, or that now carries the anchor, fails as stale. An exemption can never be forgotten silently; it can only be un-earned visibly, in a diff someone reviews.

Standalone like `test-command-blocks.sh` and `test-command-size.sh`: absent from `test-aimi-cli.sh`'s `PARTS` array, contributing nothing to its `EXPECTED_ASSERTIONS`.

## Spec Section Contract Ratchet

`commands/references/spec-section-contract.md` states, once, the section-number contract several commands, agents and one script already depend on when they parse a Claude Design handoff bundle's `BusinessSpec.md`/`DesignSpec.md` — one row per `BusinessSpec § N[.N]`/`DesignSpec § N[.N]` number a current reader relies on. Stating it once does not reach a citation added after the fact, so `scripts/test-spec-section-contract.sh` derives the citation set from the tree on every run and refuses to be green while any derived citation is neither enumerated in the contract nor a reasoned exemption — see root `CLAUDE.md` § Testing for when to run it.

**The candidate set is the union of `command_block_files()`'s corpus, never a hand-written list.** For every file under `commands/`, `agents/` and `skills/*/SKILL.md`, the suite greps the file's FULL TEXT — never only its bash blocks, since a citation lives in ordinary prose — for `(BusinessSpec|DesignSpec) § [0-9]+(\.[0-9]+)?`, and takes one candidate per distinct (file, citation) pair. `spec-section-contract.md` excludes itself from its own corpus, by file identity rather than by a hardcoded relpath string, the same self-reference exclusion its own "Re-measuring This Contract" section applies when it re-derives the citation set it is required to cover.

**A citation is covered by a literal substring match against the contract file, never a structural table-row parse** — the same fidelity `spec-section-contract.md`'s own re-measurement command uses, and the same fidelity `test-artifact-language.sh`'s Form R matching uses. This is a known, accepted limitation shared with that sibling ratchet's own string-literal matching: a citation that happens to appear in the contract's explanatory prose, rather than its table, reads as covered. It also means a bare citation is covered by a longer one that contains it as a prefix — `DesignSpec § 2` is a substring of a table row citing `DesignSpec § 2.2` — which is intentional: the contract's table documents `§ 2.2` as the numbered subsection a bare `§ 2` citation names.

**`spec-section-contract-baseline.txt` carries two kinds of tab-separated line** — `contract-path` (declared once, naming the file every citation is checked against) and `exempt` (a `<relpath>#<citation>` pair the corpus scan derives but the contract genuinely should not enumerate). `exempt` REQUIRES a `#`-prefixed one-line reason, the same per-line-reason shape `command-blocks-baseline.txt` and `artifact-language-baseline.txt` already use — and the same file is a ratchet in **both** directions, the rule `command-size-baseline.txt` states for its own byte budgets: an `exempt` entry naming a (file, citation) pair whose citation string no longer appears in that file, or that the contract now enumerates, fails as stale.

Standalone like `test-command-blocks.sh`, `test-command-size.sh` and `test-artifact-language.sh`: absent from `test-aimi-cli.sh`'s `PARTS` array, contributing nothing to its `EXPECTED_ASSERTIONS`.

## Plan Router Layout

`commands/plan.md` is a router. For each phase it keeps the heading, an `Applies when:` condition that can be evaluated from state the file already holds (with the default to apply when it does not hold, so every variable a later phase reads is still set), and a `Read` line naming the phase's file under `commands/references/plan/`. The body of the phase lives in that file and is read only when the condition holds. A `## Phase Files` section near the top states the mechanism once.

- **Measured in release 1.152.0.** `plan.md` is 16362 bytes, under the shared 16384-byte ceiling, so it no longer needs a line in `scripts/command-size-baseline.txt`. The 44 files under `commands/references/plan/` total 430023 bytes, the largest being `phase-1-9-foundation-conditions.md` at 16218 (the next, `phase-3d-expander-prompt.md`, is 16131). The file count and the router are as they were at `78df52f`; the total grew by 20401 bytes from the outline contract, the wave dispatch and the outline-edit path in the Phase 3 files (to 427973 by 1.151.0), and by 2050 more from the rail, path and `outputs` wording in five Phase 3d, 3d.5, 3e and 4 files. What every `/aimi:plan` run loads before it has read a single phase file went from 400085 bytes (`plan.md` at `7bf8315`, the commit before the split began) to 16362. Re-measure with `wc -c` rather than quoting these.
- **The classification is `commands/references/context-budget.md`'s, cited and not restated.** The condition stays in the parent because it is cheap and always needed; only the body, which most runs never need, is lazily read — that file's § The Cheap-Condition-In-The-Parent Rule is the reason the split is shaped this way, and § The Three-Way Classification is where a new piece of plan content is sorted.
- **Re-read after compaction.** `plan.md` carries the rule **When the conversation resumes after a context compaction, re-read the current phase's file before continuing**. A phase file's text does not survive compaction; the router does, so the router is where the rule lives. `check_plan_md_carries_reread_after_compaction_rule` fails if it is deleted.
- **A moved section is cited by the file that holds it.** A `plan.md § <heading>` citation resolves in `plan.md` or in a file under `references/plan/`; when a heading moved, the citation moved with it (the Phase 3e Project Path Gate is now `references/plan/phase-3e-story-merge.md`). A phase file opens with a `# Plan: <title>` heading and a note that its section moved from `plan.md` verbatim.
- **The structural test is `scripts/tests/test_plan_wiring.py`,** part of the ordinary `python3 -m pytest plugins/aimi-engineering/scripts/tests/ -q` run, with `scripts/tests/plan_text.py` as the one reader of "the plan's text" (references first in sorted order, router last, so a heading slice finds the moved body before the router stub of the same name). Its five checks are over a corpus dict and each is shown to go red on a damaged copy (`test_checks_go_red_on_broken_copy`): Phase 3d.5 carries no optional wording; it names `apply-audit-patches` and the deferred flag; no `story-merge` call carries a gate-escape flag; every file under `references/plan/` has both an `Applies when:` condition and a `Read` line in the router (an orphan reference fails); and the compaction rule is present. `AIMI_PLAN_WIRING_ROOT` points the checks at another `commands/` directory.
- **Phase 3d.5 reads from disk.** The auditor (`tools: Read`) reads the staged `NN-*.json` files, `outline.json`, the research files and `RUN_DIR/consolidation.md` from absolute paths in its prompt; nothing is inlined and nothing is truncated by an inline cap. The sidecar `consolidation.md` holds the Phase 1.6 summary: each audit attempt writes it only when it is missing or empty, so a retry reuses it, and Edit outline rewrites it. `story-merge` lists only `.json` names, so the sidecar is never read as a story. A sidecar still missing or empty after that step takes the Failure Fallback. **Retry audit:** only when `audit-result.json` is the `audit-failed` stub (its `status`, never the `_audit` sentinel, which `apply-audit-patches` also writes for a malformed entry), the Unresolved Gate offers Retry audit, Defer with reason, Edit outline and Abort, Retry audit first and Apply anyway not offered, for at most two retries (`auditRetries`); after that the normal four options return. Agent mode retries once, then auto-defers. The retry re-enters at the `consolidation.md` step and never re-expands a story. `test_auditor_reads_run_dir.py` and `test_retry_audit_option.py` pin the spawn and the gate.
- **Phase 3d runs every batch of expanders inside the Working Tree Guard** (`references/plan/phase-3d-tree-guard.md`). The orchestrator records `git status` and the stash of every repository under AIMI_ROOT, ignoring `.aimi/`, before a wave, a retry or a re-expansion, and compares them after it returns; a difference stops the plan and shows the diff, and nothing is reverted automatically. It exists because expanders, which hold every tool, edited the repository and ran a bare `git stash` to try a story. It is detection, not prevention, and it works on both hosts; `scripts/tests/test_tree_guard.py` runs the block under bash and zsh.
- **Measured at release 1.156.0, from the merged tree.** `commands/references/plan/` holds 46 files totalling 445331 bytes (1.152.0 counted 44: `phase-3d-tree-guard.md` arrived in 1.155.1 and `phase-3d-context-files.md`, 6109 bytes, in this release), and `plan.md` is 20816 bytes and carries its own line in `scripts/command-size-baseline.txt`. Re-measure with `ls commands/references/plan/*.md | wc -l` and `cat commands/references/plan/*.md | wc -c` rather than quoting these; the 1.152.0 bullet above stays as the record it is.
- **Shared expander context files** (`references/plan/phase-3d-context-files.md`, read by the router's Phase 3d entry). Before the first spawn the orchestrator writes the blocks every expander shares (outline, consolidated research, resolved decisions, prior planning gaps, design decisions, the two specs, the prior-phase handoff, one foundation proposal per accepted root) under `<RUN_DIR>/context/` and hands each spawn their paths. The run sets `expanderContextMode` once, to `files` when every Write succeeded and no file is empty and to `inline` otherwise, and never mixes the two forms, not across waves and not for a retry; a re-spawn whose shared inputs changed rewrites the affected file first and stops the batch if that fails. Section-scoped research excerpts, view-scoped prototype excerpts and the producer slice stay inline because they differ per outline entry. The hook rule that makes the files read-only to an expander is under `### Staging-file guard`, and `scripts/tests/test_expander_context_wiring.py` pins the reference, the router entry and the agent file, including a new shared block left inline.
- **The validation stamp is written in Schema Validation** (`references/plan/phase-3d-validate-retry.md`): once a staged story passes steps 2 and 2b the orchestrator writes `NN-<slug>.json.validated` beside it holding the sha256 of the file, and from then on the hook refuses every Write and Edit of that story. Until the stamp exists a subagent, which is the expander re-spawned for the defect, may overwrite its own unstamped file. The mechanism and its limits are under `### Staging-file guard`.
- **Phase 2.4 resolves only factual questions** (`references/plan/phase-2-4-codebase-cross-check.md`). The batched symbol extractor (`agents/workflow/aimi-spec-flow-symbol-extractor.md`) returns `{"<anchor>": {"kind": ..., "symbols": [...]}}` with `kind` from the closed set `existence`, `location`, `behavior`, `policy`, `design`, `other`. The orchestrator validates `kind` as untrusted output, by exact case-sensitive match: only `existence` and `location` go on to symbol validation and the grep; `behavior`, `policy`, `design` and `other` are held back with no grep and no `oqDecisions[]` entry, and anything else (a missing anchor, an unknown kind, a value that is not an object with a `symbols` array, a legacy bare-array reply) fails closed as `unclassified`. A held-back anchor reaches Phase 2.5, and the log line gains an optional `; held back: <kind>=<n>, ...` clause. `scripts/tests/test_phase_2_4_question_kind.py` pins it.
- **Design-bundle detection filters by relevance** (`references/plan/phase-0-design-bundle-detection.md`): the feature description goes to `detect-design-bundle --feature-stdin`, see `### detect-design-bundle --feature-stdin` below. The design-bundle import slug comes from the `slugify` verb, see `### slugify`.
- **What the router does not do.** It does not make a phase optional: a false condition skips the file, never the default beside it. It is not a place for a deterministic procedure either — that still belongs in an `aimi-cli.sh` verb, as the audit patch application did.

### OpenCode references translation allowlist

`install.sh` copies the whole plugin tree verbatim (`cp -R "$src/."`), so `commands/references/` reaches OpenCode untranslated, deliberately: most references document Claude Code behaviour on purpose. Only the files named in `REFERENCE_ALLOWLIST_FULL` and `REFERENCE_ALLOWLIST_LITERALS` are then rewritten in place by `install_references`, which runs right after the copy. Patterns are relative to `commands/references/` and may be globs.

- **`REFERENCE_ALLOWLIST_FULL`** is `plan/*.md` and `execute/*.md`: the host-literal rewrite (plugin root variable, the `/plugin install` message, the `AskUserQuestion` rules, the Task spawn mapping) plus the config-dir rewrite, the treatment a command body gets minus the agent-invocation preamble and the `general-purpose` swap, which are command-entry-point behaviour. It is a glob so a split file added later needs no edit, and because those files carry the inline CLI resolution and the picker wording that used to be in `plan.md` and `execute.md`.
- **`REFERENCE_ALLOWLIST_LITERALS`** is `cli-path-resolution.md`, `container-execution.md` and `user-communication.md`: host literals only. **`cli-path-resolution.md` is not config-dir rewritten** because it documents both hosts' resolution and has to keep the Claude Code cache path it describes verbatim; rewriting it would erase half of what it says. `interactivity.md` is absent on purpose, since it documents the exact strings the rewrite targets.

## Execute Router Layout

`commands/execute.md` is a router, in the shape of `## Plan Router Layout`. Each entry keeps a heading, an `Applies when:` condition evaluable from state the file already holds, an optional `Covers:` line and a `Read` line naming the step's file under `commands/references/execute/`. A `## Step Files` section near the top states the mechanism once. The body of a step lives in its file and is read only when the condition holds.

- **The default sits beside the skipped case.** Every `Applies when:` line says what happens when it does not hold (`PHASE_SPLIT_MODE=false`, `VISUAL_FOLLOW=false`, `FINALIZE_STATUS=skipped`), so a variable a later step reads is set whether or not the earlier file ran. A false condition skips the file, never the default beside it.
- **`$ARGUMENTS` stays in the command body.** The host substitutes `$ARGUMENTS` only in a command body, so a bash block under `commands/references/` that read it would see the literal text rather than what the user typed. `execute.md` therefore keeps its four argument-reading blocks (`--base`, `--push`, `--container`/`--inline` and `--phase`), and `plan.md` took its three back from `references/plan/step-0-environment-setup.md`, where they had silently lost the user's flags.
- **A file whose condition cannot be evaluated early is read with the entry that uses it.** Release the Claim on Abort is needed before the first abort after the claim, which is earlier than any condition could say, so `release-claim-on-abort.md` is read with the Step 1.7 entry instead of getting an entry of its own.
- **Spawned Tasks.** A spawned split task opens with a marker line `SPAWNED_SPLIT_TASK=<kind>` and nothing else of the conversation. The `## Spawned Tasks` table lists, per kind (`flat-split-child`, `phase-split-sub-orchestrator`), the entries it evaluates and the entries it skips; every entry heading is in exactly one of the two cells of each row, and an entry that holds is still skipped when its heading is in Skips. The spawning orchestrator hands the child the router path and the plugin root, because the host expands `CLAUDE_PLUGIN_ROOT` in the parent's copy while the child reads the file raw.
- **Three rules the router carries.** After a context compaction, the router and the current step's file are re-read and every value an earlier block echoed is re-derived, because a step file's text does not survive compaction and the router does. Step 4's in-loop state (the wave, per-group `base_sha`, the buffers) is rebuilt from `$WORKTREE_MGR list`, `list-ready` and `status`, and `is_first_story_in_session` defaults to true. A failed `Read` of a listed file is a STOP that reports the path, never the condition being false.
- **The structural test is `scripts/tests/test_execute_wiring.py`,** part of the ordinary `python3 -m pytest plugins/aimi-engineering/scripts/tests/ -q` run, with `scripts/tests/execute_text.py` as the one reader of "the execute text" (the router in document order, each reference inserted at its first `Read` line; `test_execute_text.py` pins that reader). Its checks are over a corpus dict and each is shown to go red on a damaged copy (`test_checks_go_red_on_broken_copy`): every file under `references/execute/` has a `Read` line in the router (an orphan fails), every `Read` target exists, every entry has an `Applies when:` line, no file is read by two entries, the compaction and failed-Read sentences are present, the Spawned Tasks table covers every entry, and no reference carries a bash block reading `$ARGUMENTS`. `AIMI_EXECUTE_WIRING_ROOT` points the checks at another `commands/` directory. `scripts/tests/test_arguments_stay_in_command_bodies.py` is the argument guard behind that last check, over `references/plan/` and `references/execute/` alike.

- **Split files run in waves** (`references/execute/step-0-9-split-waves.md`, added in 1.156.0). `metadata.splitGroup.after` names the sibling files whose repositories a file's stories depend on, and `split-detect` returns it as `after[]` on every member. The entry computes the waves once before the first spawn with a jq program over the active members, matching each `after` entry to a member by basename and counting an entry that names no active member (a finished file, a file outside the group) as satisfied, and prints one `{"wave":N,"file":...}` line per active member. It serves both spawn sites, **Parallel Execution for Split Files** (flat) and **Spawn Split Sub-Orchestrators** (phase mode), by replacing their single turn with one turn per wave: every Task of wave N returns before any Task of wave N+1 starts, and a split where every member lands in wave 1, including the legacy frontend/backend pair, behaves as before. A non-zero exit means a file-level cycle or self-reference, which `story-merge` refuses at plan time, so it can only come from a hand-edited file; the run STOPs before any worktree-bound Task is spawned. A dependent file runs even when a predecessor ended with failed or skipped stories, and one `[wave N] <file>: <c> completed, <f> failed, <s> skipped` line per file makes that visible. The waves are ordering only: **each dependent branches from its own base and nothing is merged between repositories, so a predecessor's unmerged code is not visible to it**, and **the SIDE axis (frontend and backend in one repository) carries no `after` and keeps a single turn.** `scripts/tests/test_split_file_waves.py` extracts the block and runs it under bash and zsh against a stub `split-detect`.
- **What the router does not do.** It does not make a step optional, and it is not a place for a deterministic procedure, which still belongs in an `aimi-cli.sh` verb. It does not shrink what a run reads when every file applies.

## aimi-cli.sh Research Subcommands

Two CLI subcommands manage the research lifecycle. Both are internal — consumed by `plan` and `deepen` commands, not invoked by users directly.

- **`research-lookup <path>`** — Content-aware freshness check. Reads the `## File References` h2 bullet section of the given research `.md` file, compares its mtime against the newest mtime of every cited source path, and exits 0 (fresh) or 1 (stale). Cited paths that are missing or outside the project root are treated as stale. Used by `plan`/`deepen` before deciding whether to spawn a researcher.

- **`extract-sections <file> --anchors "<titles>"`** — Prints the requested sections of a research file. It matches a heading of any level two or deeper (`##`, `###`, `####`, ...), not only `##`; an h1 is never matchable. A section runs from its heading to the next heading of the same or a higher level, so an h2 anchor includes its nested h3 lines and an h4 anchor stops at the next h4, h3 or h2. Anchor and heading are compared on one match key (`_extract_sections_match_key`): `"`, `\`, `$` and the backtick are removed, whitespace runs collapse to one space, the ends are trimmed and the result is lowercased, so the sanitized anchor `The foo flow` finds the heading `## The "foo" flow`. An anchor with no matching heading, or whose key is empty, is skipped with a `no section matched anchor` warning on stderr at exit 0. A raw anchor carrying `$(`, a backtick or `$` followed by a letter is rejected with a warning (defense in depth, since a double-quoted shell argument evaluates those before the CLI runs); a raw `"`, `\` or `$` not followed by a letter or `(` is accepted and compared by its key. The researcher templates therefore write `###` headings and may put those four characters in them: the planner strips them from the anchor and `extract-sections` strips them from the heading before comparing, and `commands/references/plan/phase-3d-prep-blocks.md` states the Step 2 sanitization rule (every `$`, backtick, `"` and `\` removed, newlines to spaces, 200-character cut) with nothing dropped afterwards. `extract-prototype-sections` keeps its own rejection of the four characters.

- **`research-gc`** — Orphan garbage collector. Deletes `.aimi/research/*.md` files older than 30 days that are not referenced by any active `.aimi/tasks/*.json` `metadata.researchPaths`, any `.aimi/brainstorms/*.md` frontmatter `researchPaths`, or any `.aimi/brainstorms/*.md` frontmatter `foundationProposalPath`. Called opportunistically once per `plan`/`deepen` session. Silent when nothing is removed.

## aimi-cli.sh Spec Derivation Subcommand

- **`spec-derivation --input <path>`** — Validates a research agent's entity/endpoint presence findings, shaped `{"records":[{"kind":"entity"|"endpoint","name","status":"present"|"absent"|"unchecked","evidence":[...]}]}`, and prints `{records, relabeled, markdown:{entities, endpoints}}`. A one-crossing reader with no lock, the same shape as `design-decisions`: `cmd_spec_derivation` confines `--input` with `validate_path_in_project` (it arrives as a CLI argument), calls `check_python3`, then makes exactly one crossing into `tasks.py`'s `spec-derivation` op, which owns the validation (`derive_spec_records`). `absent` is a positive claim, so a record claimed `absent` with an empty `evidence` array is relabeled `unchecked`, listed in `relabeled` as `<kind>:<name>`, and reported on stderr; a record that arrived as `unchecked` with no evidence is the genuine never-checked case and passes through unchanged, unlisted. The markdown strings hold one `| name | status-label | evidence |` row per record in input order; the status-label `unchecked (claimed absent, no evidence)` appears only on relabeled records. Malformed input exits 1 with a message naming the record index and the invalid field (`records[N].<field> ...`). Downstream callers consume this verb's output; none reimplements the validation.
- **`structural-vocabulary --tasks <path> [--spec <path>]... [--prototype <path>]...`** — Advisory count of the `STRUCTURAL_LEXICON` container/placement terms (bottom sheet, dialog, modal, ...) in a spec/prototype versus a tasks file's story text, printing `{measured, terms, missing, unsourced}`. A one-crossing reader with no lock, the same shape as `spec-derivation`: `cmd_structural_vocabulary` confines every path with `validate_path_in_project`, calls `check_python3`, then crosses once into `tasks.py`'s `structural-vocabulary` op. Matching is whole-phrase and case-insensitive (`playlist` is not `list`); `measured` is false, with empty arrays, when no term occurs anywhere. It never blocks; the caller decides how to present `missing` and `unsourced`.

## aimi-cli.sh Story Lifecycle Subcommands

### One-crossing invariant (structural, and mechanically checkable)

**Every `tasks.json` verb wrapper in `aimi-cli.sh` makes exactly one crossing into Python, and for a writer that crossing is inside the lock.** The shape is `( _lock "$f.lock"; python3 tasks.py <op> … ) 200>"$f.lock"` — read, decide, write and return, all within the single call. A wrapper that crosses twice has, by construction, a read that happens outside the lock it then writes under, and something can change in between.

**The check is counting `python3` invocations per wrapper, over the wrappers selected by the LOCK.** That is the whole point of writing this down: *"did concurrency change?"* is a behavioural question a reviewer cannot answer by reading a diff, and *"how many times does this wrapper call `python3`?"* is a structural one they can. In a tasks verb, more than one crossing is the defect and **zero is the same defect wearing jq** — a wrapper that never reaches Python is doing its own read-decide-write in bash, which is the shape this invariant exists to forbid. `test_every_locked_tasks_verb_crosses_into_python_exactly_once` in `scripts/tests/test_tasks.py` enforces it; `scripts/test-tasks-concurrency.sh` is what demonstrates the consequence.

**Selecting on the crossing is how a wrapper hides from the count, and that is not hypothetical.** That test's filter used to require a crossing to be present before it would count crossings, so `set-execution-mode` — which took `"${tasks_file}.lock"`, read its phase guard with `jq` *outside* it and wrote with a second `jq` *inside* it — was discarded before the exhaustive comparison ran, and the word "every" above was false for as long as it stood. The filter selects on the lock now, and the two failure modes report themselves separately so neither is read as the other's diagnosis. A locked tasks wrapper making zero crossings is exercised as a fixture in the same file, so the widened check is shown to bite rather than merely to pass.

Two exemptions exist, both in the roadmap family, both named here so the list cannot grow quietly:

- **`roadmap-init`** and **`roadmap-amend-phase`** cross twice on purpose. A payload arrives on **stdin** and can be refused without reading `roadmap.json` at all — malformed JSON, a bad `creates`/`needs` identity, an unamendable key. Refusing inside the lock would create the feature directory as a side effect of saying no, so the payload is validated in its own crossing first. `cmd_roadmap_set_status` carries the normative statement of this in a comment beside its own single crossing.
- **No `tasks.json` verb takes a stdin payload**, so none of them has that exemption available. Every refusal a tasks verb can reach without the document — a missing argument, a malformed story id, an unknown flag — already happens in bash before the lock; every remaining one needs the file, and a second call could only re-read what the first one holds.

Readers are exempt from the lock half and not from the counting half. `cmd_list_ready` names the module in each of two mutually exclusive branches, which is one crossing per invocation; that branch exemption is asserted by name too.

The same counting rule covers the four **`models.json` readers** — `cmd_resolve_models`, `cmd_get_current_models`, `cmd_models_prompt_check` and `cmd_list_models`, each one crossing into `scripts/models.py`, none of them taking a lock (`test_each_reader_crosses_at_most_once_per_invocation` in `scripts/tests/test_models.py` counts them). `cmd_list_models` is the second **branch** exemption after `cmd_list_ready`, and the opposite shape: its Claude Code branch crosses ZERO times, because that host's answer is a constant. Zero crossings is the defect in a tasks verb — there it means a read-decide-write done in bash — and is not one here, where nothing is read and nothing is decided. The three aliases it prints are consequently spelled twice, once as data in `_host_valid_models` and once as JSON in the branch; the two are run against each other by `test_list_models_claudecode_matches_the_host_valid_set` so the second cannot drift. **None of the four calls `check_python3`** — see the top-level `CLAUDE.md` § Testing for why that would be a regression, and what each degrades to instead.

`cmd_detect_models`, the **writer** of that same file, is counted by the same rule (`test_the_writer_crosses_once_and_the_assembly_is_written_once`) and answers the `check_python3` question the other way: it calls it and refuses, because a writer has no honest degrade — see the top-level `CLAUDE.md`. It takes no lock either, and that is deliberate rather than an oversight: nothing else writes `models.json`, and `write_aimi_models_config`'s mktemp-then-`mv` is what makes a concurrent reader see one whole document or the other, never half of one. Its merge lives in `merge_models_document`, whose first parameter is the existing document **so that a rebuild cannot be written there by accident** — that shape is what shipped as 1.97.2, dropping the inactive host's models on every invocation, and the assembly was duplicated verbatim across two branches precisely because the fix was copied from one to the other.

### `remove-story`

- **`remove-story <id> --reason <text> [--tasks-file <path>]`** — Withdraws a pending, dependency-free story from a plan and records why, so a scope cut is a single auditable command instead of a hand-edited `tasks.json`. Prints `{id, removed: true, remaining}` on success.

  **The one deliberate exception to the mark-* wrapper shape it is otherwise modelled on.** Every mark-* verb (and `update-field`) has `cmd_...` call `validate_story_exists` in bash, *before* the lock — this one does not. Every refusal is decided by `tasks.py`'s `op_remove_story`, inside the single crossing, in this fixed order: not found → not pending → has dependents → the only story left in the file → `--reason` missing or empty. The order is load-bearing: a caller targeting a nonexistent id must see "not found" rather than a later-stage message, and a race that adds a dependent edge, or drops the story's status out of `pending`, while `remove-story` waits for the lock is judged against the document as it is *inside* the lock, not against a bash-side read taken before it (`test-tasks-concurrency.sh`'s `test_remove_story_refuses_a_dependent_added_under_it` demonstrates the latter). The only bash-level gate ahead of the crossing is the CLI-shape check for a missing story-id argument (plus `validate_story_id`'s format check and the usual path resolution/confinement) — never a document-dependent precondition.

  - **Not found** — exits 1, names the id, says it was not found. Writes nothing.
  - **Not pending** — a story whose status is `in_progress`, `completed`, `failed` or `skipped` is refused, naming both the id and its actual status. Writes nothing.
  - **Has dependents** — refused when at least one *other* story's `dependsOn` lists this id, naming **every** dependent (not just the first). Writes nothing.
  - **Last story in the file** — refused when the target is the only entry in `userStories`, since removing it would leave an empty plan. The message names the way out, and it depends on `metadata.phase`: a phase-scoped file (`metadata.phase` present) is pointed at `roadmap-set-status --status cancelled`; a flat file (`metadata.phase` absent) is pointed at `archive-task`. Writes nothing.
  - **`--reason` missing or empty** — refused, naming `--reason` as required. Checked *inside* `op_remove_story`, not by an `aimi-cli.sh` pre-check, so this is the one refusal among the five that genuinely needs no document read yet still crosses — see the note above about why nothing here shortcuts to bash. Writes nothing. `cmd_remove_story` builds the `--reason <text>` flag only when the value is non-empty (the same rule `cmd_mark_complete` applies to `--evidence`), so an empty `--reason ""` and an omitted one reach `tasks.py` identically.

  **On success**, the story is removed from `userStories` and one entry is appended to `metadata.decisions` (the array is created if absent) — the first Python-side writer of that field anywhere in this file; every other entry is written command-side, at plan time. Shape: `{"anchor": "removeStory:<id>", "source": "removeStory", "text": "<sanitized story title>", "resolution": "removed: <sanitized reason> (<YYYY-MM-DD>)"}`. Both the story's own title and the `--reason` text are sanitized through `sanitize.py`'s `rm_sanitize` (the one prose sanitizer `roadmap.py` and `story_merge.py` already import — see the top-level `CLAUDE.md` § Testing) at a 2000-character cap. Removing a story nothing depends on cannot open a wave gap, so no other story's stored `wave` needs to change, and `validate-deps`/`validate-ids`/`validate-waves` all stay valid on the resulting file.

### `set-verification`

- **`set-verification <id> <passed|failed|skipped> --reason <text> [--tasks-file <path>]`** — Writes `verification.status` (and, for `skipped`, `verification.skipReason`) in one locked crossing, so a verdict can never be recorded without saying why it was skipped. Prints `{id, verification}` on success — the whole post-write `verification` object, the same `field_payload` echo-back shape `update-field` already uses. This is the verb `roadmap.py`'s `VERIFICATION_GATE_NOTE` points an operator or `/aimi:execute` at instead of a raw `update-field <id> verification.status <value>` write.

  **Modeled on `remove-story`'s shape, not on the mark-* wrapper shape.** Every refusal is decided by `tasks.py`'s `op_set_verification`, inside the single crossing, in this fixed order: status outside the allowed set → a `--reason` mismatched to the status → not found → no verification object to update. `cmd_set_verification` bash-validates neither `$status` against passed/failed/skipped nor pre-lock via `validate_story_exists` — both are document-dependent (or document-set-vocabulary-dependent) refusals `op_set_verification` owns, the same exception `cmd_remove_story`'s own comment documents; a bash-side status literal here would be the second list the shared-context cross-story contract forbids (`VERIFICATION_STATUSES`/`VERIFICATION_STRATEGIES` live once, in `tasks.py`, beside `GATE_KEYS`).

  - **Status outside the allowed set** — `pending`, or any value not in `VERIFICATION_STATUSES`, is refused naming `passed`/`failed`/`skipped` as the allowed values. `pending` is excluded on purpose: recording a verdict is the opposite of "nobody looked yet", so this verb can never write it back. Writes nothing.
  - **A `--reason` mismatched to the status** — `skipped` with a missing or whitespace-only `--reason` is refused, naming `--reason` as required; `passed`/`failed` with a non-empty `--reason` is refused, naming `--reason` as accepted only alongside `skipped`. Writes nothing either way. `cmd_set_verification` builds the `--reason <text>` flag only when the value is non-empty (the same rule `cmd_remove_story` applies to its own `--reason`), so an empty `--reason ""` and an omitted one reach `tasks.py` identically.
  - **Not found** — exits 1, names the id, says it was not found. Writes nothing.
  - **No verification object to update** — refused when the matching story's own `verification` field is absent or not a JSON object, naming that there is nothing to update. Writes nothing.

  **On success**, every matching story (the same `_selected_slots`-driven "every match, not the first" semantics `mark_stories`/`assign_field` share, for a tasks file that carries a duplicated id) is rewritten through `write_verification_verdict(story, status, reason)` — the ONE mutation point a verification verdict is ever written through, documented as such so an evidence-derived verdict (`judge-verification`, below) and this operator-typed one share exactly one path. It copies the existing `verification` object, sets `status`, and for `skipped` sets `skipReason` to `reason` sanitized through `rm_sanitize` at `VERIFICATION_SKIP_REASON_MAXLEN` (500) — for every other status it POPS any stale `skipReason` key, so a `passed`/`failed` verdict recorded after an earlier `skipped` one never leaves the old reason sitting beside the new verdict.

  **`update-field` gained a matching, narrower guard of its own, at the same time.** `verification.status` and `verification.strategy` are the two leaf paths a verification verdict is ever written through raw, so `op_update_field` now refuses a value outside `VERIFICATION_STATUSES`/`VERIFICATION_STRATEGIES` on those two exact dotted paths — checked by exact string equality on the WHOLE path, before `read_docs`, so `verification` alone (the golden `update-field-sobrescreve-objeto` case, which replaces the whole object with the string `"manual"`) is untouched and `update-field` stays a general nested writer everywhere else. `update-field` still accepts `pending` on `verification.status` (unlike `set-verification`, which never writes it) — the guard bounds the vocabulary, it does not adopt `set-verification`'s narrower one.

### `acknowledge-smell`

- **`acknowledge-smell <story-id> --type <smell-type> --reason <text> [--tasks-file <path>]`** — Records a reasoned acknowledgement on a `metadata.smellWarnings` entry, so `roadmap-set-status --status completed` can be unblocked by command instead of a hand edit of `tasks.json`. Prints the post-write entry as JSON. This is the verb `roadmap.py`'s `VERIFICATION_GATE_NOTE` names beside `set-verification`.

  **Refusal order, fixed.** The wrapper decides first, in bash, before the lock: a malformed story id (`validate_story_id`), then `detect-interactivity` resolving to `agent` (`AIMI_AGENT_MODE=true`, `CI=true` or `--non-interactive`) — an acknowledgement needs a human decision, so the message says so, and it is checked before the lock because it needs no document. Then, inside the single crossing in `tasks.py`'s `op_acknowledge_smell`: `--reason` empty or whitespace-only (message names `--reason`), then no entry matching `storyId` + `type` (message names the story id and the type). Every refusal exits 1 and writes nothing. Tests that exercise the success path must unset `CI` and `AIMI_AGENT_MODE`.

  - **Matched by `storyId` + `type`, never by array index.** Every matching entry is acknowledged (a story can carry two of one type); entries for another story or another type are left byte-for-byte unchanged.
  - **Success shape.** `acknowledged: true` (the JSON literal — the only value the completed gate counts), `acknowledgedReason` (sanitized through `rm_sanitize` at `SMELL_ACKNOWLEDGE_REASON_MAXLEN`, 500) and `acknowledgedAt` (ISO-8601 UTC). The first matching entry is what is printed.
  - **Idempotent.** An entry already acknowledged with the same sanitized reason is a no-op success: nothing is written and the first call's `acknowledgedAt` is preserved. A different reason on an already-acknowledged entry replaces the reason and the timestamp together.
  - **One crossing, inside the lock** — `( _lock ...; python3 tasks.py acknowledge-smell ... ) 200>`, counted by `test_every_locked_tasks_verb_crosses_into_python_exactly_once`; the op is registered in `_OPS` and in the literal set of `test_every_op_is_named_after_the_verb_that_calls_it`.
  - **`story-merge` regenerates `smellWarnings`**, so a re-merge of a plan resets every acknowledgement; acknowledge after the final merge.
  - **Intentional shape difference from the evidence acknowledgement** (`metadata.evidenceAcknowledged` = `{reason, acknowledgedAt, completed}`, outline:05): this verb writes flat `acknowledged`/`acknowledgedReason`/`acknowledgedAt` on the smell entry itself, because the smell entry already is the per-story record and `_unacknowledged_verify_coverage` reads `acknowledged` off it. The two share the contract — reason required and sanitized at 500, UTC timestamp, agent-mode refusal before the lock, idempotent no-op preserving the first timestamp — and differ only in container shape.

### `acknowledge-evidence`

- **`acknowledge-evidence --reason <text> [--tasks-file <path>]`** — Records, on a tasks file's `metadata`, that a human saw a phase whose completed stories carry no discriminating evidence and chose to let it close, so `roadmap-set-status --status completed` can be unblocked by command. Prints the written record as JSON. This is the verb `roadmap.py`'s `VERIFICATION_GATE_NOTE` names beside `acknowledge-smell`.

  **The gate it unblocks.** `roadmap-set-status --status completed` now refuses a phase that has at least one completed story and in which NO completed story carries `verification.evidence.discriminating` as a proven integer above zero, aggregated across **every** member tasks file of the phase (`_completed_gate_resolve_members`). The partition is `verification-report`'s own `discriminating` partition — `_completed_gate_refusals` calls `verification_report` and counts `checked`/`blind`/`unrecorded` out of it, so the rule lives once in `tasks.py`'s `_report_discriminating`: an absent key, `--evidence '{"exit":0}'`, a recorded `0`, a float or a string all count as not proven, and **a JSON boolean is never a count**. The refusal line states `discriminating=<n> completed=<m>` and names `acknowledge-evidence`. `--force` does not reach it, the same as the handoff and verification preconditions. `mark-complete` is deliberately unchanged: the gate is at the phase close, not at the story.

  **Refusal order, fixed.** The wrapper decides first, in bash, before the lock: `detect-interactivity` resolving to `agent` (`AIMI_AGENT_MODE=true`, `CI=true` or `--non-interactive`) — checked before the lock because it needs no document. Then, inside the single crossing in `tasks.py`'s `op_acknowledge_evidence`: `--reason` empty or whitespace-only (message names `--reason`). Every refusal exits 1 and writes nothing. Tests that exercise the success path must unset `CI` and `AIMI_AGENT_MODE`.

  - **Schema key `metadata.evidenceAcknowledged`** = `{reason, acknowledgedAt, completed}`: `reason` sanitized through `rm_sanitize` at `EVIDENCE_ACKNOWLEDGE_REASON_MAXLEN` (500), `acknowledgedAt` ISO-8601 UTC (`%Y-%m-%dT%H:%M:%SZ`, the format `acknowledge-smell` stamps), `completed` the integer completed-story count the acknowledgement was recorded against.
  - **Lapse.** The gate honors the key only while `completed` equals the phase's CURRENT aggregate completed-story count. When the count has changed since — a story completed or a sibling was re-merged — the gate refuses again and the refusal says the acknowledgement lapsed. A `completed` that is a boolean or a string, or a blank `reason`, is not an acknowledgement at all.
  - **Split phases.** `completed` is the PHASE-AGGREGATE count (this file plus every `metadata.splitGroup` sibling, or the legacy frontend/backend counterpart). The verb writes only into the one `--tasks-file` it is given; the gate honors an acknowledgement found in ANY member whose `completed` equals the current aggregate. `story-merge` regenerates `metadata`, so a re-merge resets it.
  - **Idempotent.** The same sanitized reason at the same completed count is a no-op success: nothing is written and the first call's `acknowledgedAt` is preserved. A different reason or count replaces the whole record.
  - **One crossing, inside the lock** — `( _lock ...; python3 tasks.py acknowledge-evidence ... ) 200>`, counted by `test_every_locked_tasks_verb_crosses_into_python_exactly_once`; the op is registered in `_OPS` and in `test_every_op_is_named_after_the_verb_that_calls_it`. `hooks/auto-approve-cli.sh` carries no entry for it, as it carries none for `set-verification` or `acknowledge-smell`: a human-decision verb is meant to prompt.
  - **Echo.** `commands/references/execute/step-5-completion.md` and `commands/references/execute/phase-completion-handoff-and-mark.md` print `evidence-acknowledged: <reason> (<acknowledgedAt>)` in the completion report and add the same as one free-prose `deviations` bullet in the phase handoff when the key is present. The read goes through `$AIMI_CLI metadata` (with `--tasks-file` in phase mode), never a `jq` of the file, so the `commands/` file-opening census above does not move.
  - **Two shapes on purpose.** `acknowledge-smell` writes flat `acknowledged`/`acknowledgedReason`/`acknowledgedAt` on the smell entry, because the entry already is the per-story record; this verb writes `reason` *inside* the one `metadata.evidenceAcknowledged` object, because the thing acknowledged is the phase's evidence as a whole. The two share the contract (reason required and capped at 500, UTC timestamp, agent-mode refusal before the lock, idempotent no-op) and differ only in container shape.

### `judge-verification`

- **`judge-verification <id> [--tasks-file <path>]`** — Derives a verification verdict from the story's own recorded verify evidence, rather than a caller typing one in. This is the verb the non-visual merge branch of `commands/references/execute/step-4-wave-execution-loop.md` calls in place of the blanket `update-field <id> verification.status passed` rewrite it used to run — a rewrite that recorded "passed" whether or not the story's own check had ever run. Prints `{id, judged, verification|reason}` on success: `judged: true` with the post-write `verification` object when a verdict was written, `judged: false` with a `reason` string when nothing was — including the "not found" case, which this verb REPORTS rather than refuses (see below).

  **Mirrors `cmd_update_field`'s bash shape, not `cmd_set_verification`'s.** `cmd_judge_verification` calls `validate_story_id`, resolves `--tasks-file` through `validate_path_in_project`, and runs `validate_story_exists` *before* the lock — because unlike `set-verification`, nothing about this verb's outcome is a status/reason pair a caller typed and might get wrong; the one thing left to decide is document-dependent (the story's own evidence), and that decision belongs to `tasks.py`'s `op_judge_verification`, inside the single crossing.

  `op_judge_verification` decides, in this fixed order, for every matching story slot independently (the same "every match, not the first" semantics `set-verification` shares — a duplicated id can report one `judged: true` and one `judged: false` line):

  - **No verification object** (absent or not a JSON object) — `judged: false`, writes nothing.
  - **`verification.strategy` is `"visual"`** — `judged: false`, writes nothing; a visual verdict is judged by the visual writers in `commands/references/execute/step-4-wave-execution-loop.md`, never by this verb.
  - **`verification.status` is not the literal `"pending"`** — `judged: false`, writes nothing, naming the current status; a story already judged (by this verb, by `set-verification`, or by a visual writer) is never overwritten.
  - **Otherwise, the verdict comes from `verification.evidence.exit`** (the field `mark-complete --evidence` persists, per `mark-complete`'s own evidence handling): a usable integer `0` writes `"passed"`; any other usable integer writes `"failed"`; anything else — no `evidence` object, no `exit` key (including a story that recorded only `preExit`), or an `exit` that is not a plain integer — is "no usable exit" and writes `"skipped"`. **A JSON boolean exit is never read as the integer `0`**: `isinstance(x, bool)` is checked before `isinstance(x, int)`, the identical guard `_report_discriminating` already applies to `.evidence.discriminating`, reused by the sibling helper `_evidence_exit` rather than re-derived.
  - **The `skipped` `skipReason` is one of exactly two literal strings**, chosen by whether `story.implementation.verify` is a non-empty string: `"implementation.verify was declared but the executor recorded no verify evidence"` when it is, `"no implementation.verify was declared, so no check ran"` when it is absent, null, or empty. Both live as module-level constants in `tasks.py` (`JUDGE_VERIFICATION_NO_EVIDENCE_REASON`/`JUDGE_VERIFICATION_NO_VERIFY_REASON`) so the op and its own pytest coverage read the identical text rather than one recomputing what the other asserts.

  **A verdict, once computed, is written through the same `write_verification_verdict(story, status, reason)`** `set-verification` uses (see above) — the ONE mutation point, so the two verbs can never disagree about how a verdict lands on disk, only about how it is derived. `write_docs_atomically` runs only when at least one matching slot actually got a verdict; a call that only produces `judged: false` results writes nothing at all, which is what the "leaves the document unchanged" acceptance criterion depends on.

### `triage-verify`

- **`triage-verify <id> [--tasks-file <path>]`** — Static findings for the `implementation.verify` of a story that has already failed; prints `{id, findings, shipped}`. Read-only and lock-free, one crossing into `op_triage_verify` in `tasks.py`, which imports `plan_checks` inside the function. The wave loop's failure branch in `commands/references/execute/step-4-wave-execution-loop.md` calls it and records the finding in the story's failure notes. It runs only `SHIPPED_TRIAGE_DETECTORS`, which as of release 1.154.0 is `("pipefail-grep-q", "git-diff-unstaged")`: the two detectors the backtest shipped (below). ### `story-merge`

One CLI subcommand manages the story-merge lifecycle. It is consumed by the `/aimi:plan` two-pass pipeline, not invoked by users directly.

- **`story-merge`** — Consolidates per-story JSON staging files written by Pass 2 sub-agents into a single validated `tasks.json`. Key behaviors:
  - **Deterministic ID assignment**: each staging file receives a stable `US-NNN` identifier in outline order.
  - **dependsOn token remapping, and the same token in story text**: `outline:NN` is the zero-padded idx in the staged FILENAME (`NN-slug.json`), never a position in the merged array, so after a skipped expansion the two disagree and resolving by position would repoint every later reference at the wrong story. `outline_map` builds `{staged idx: US-NNN}` once and both passes read it. `remap_outline_tokens` resolves `dependsOn` entries (an idx with no staged file becomes `UNRESOLVED_OUTLINE:<idx>` and the merge refuses). `remap_story_text_tokens` then resolves every `OUTLINE_TOKEN` (`outline:` plus exactly two digits not followed by a third, so `outline:7` and `outline:041` are text it does not own) in the string fields `_rewrite_story_text` walks: `implementation.approach`, `implementation.verify`, `implementation.guardRails[]`, `tasks[]`, `notes`, `acceptanceCriteria[]`, `gate.prompt` and `gate.options[]`. A token naming an idx with no staged file is left in place and the merge refuses, listing one `US-NNN <field path>: outline:NN` line each, so a reference is never dropped and never resolved by position. A field is assigned only when its text changed, which makes a second application a no-op. `verify` and `guardRails` take the same substitution, so a rail that equalled a verify segment before the merge still does. An `outline:NN` that survives anyway, because it was one digit or three, is reported by the `leftover-outline-token` smell (see `### Advisory smells`).
  - **Split re-render**: a split renumbers each output file from `US-001`, so a `US-NNN` cited in story text stops naming the story it meant. After `--split full-stack` the writers rewrite every `STORY_ID_REF` in the same fields through `_render_split_refs`: a target in the same file reads as its new id, a target in another file reads as its new id plus a label (`frontend`/`backend` on the SIDE axis, the project key on the PROJECT axis, `root` for `"."`). `verify` and `guardRails` get the bare id only, since a parenthesis there is a shell syntax error.
  - **Verify refusal**: before any remap or sweep, a story whose multi-line `implementation.verify` can swallow a failing line refuses the merge, naming `US-NNN` and its staged idx. It has no `--agent-mode` exemption, because an audit patch can introduce the verify after the expansion-time check ran. The rule is `tasks.py`'s `verify_composition_findings`, shared with `validate-staging` and `validate-tasks` R23; see `### validate-staging`.
  - **Rail and path refusal**: in the same spot, right after the verify refusal and ahead of every remap and sweep, a story with a guard rail that is not a whole top-level segment of its `verify`, an `implementation.files` entry outside its repository, or a malformed `implementation.outputs` refuses the merge, one line per finding naming `US-NNN` and its staged idx (`rail_and_path_refusal_lines`, which reads `rail_and_path_findings`, the function `validate-staging` reads too). It has no `--agent-mode` exemption for the verify refusal's reason: an audit patch can introduce the shape after the expansion-time check ran. It reads only the staged stories in hand, so a tasks file already on disk is never revalidated or changed, and nothing is written when it fires.
  - **DAG validation**: cycle detection aborts the merge before any write.
  - **Wave computation**: BFS over the dependency graph assigns each story to a parallelism wave.
  - **Post-merge sweeps**: Rule 22 mock-sync AC routing, Phase 3.1 Reference Element Inventory verdict check, and Phase 4.1 Coverage Self-Check run after DAG validation and before the atomic write.
  - **Audit gate**: a staging directory holding two or more `NN-*.json` story files is refused unless it carries an `audit-result.json` whose `auditedIdx` equals the staged idx set. It runs first, before any story is read, and has no flag, environment variable or `--agent-mode` exemption. See `### apply-audit-patches` and the story-merge audit gate below.
  - **Advisory smells**: `field-overlap`, `story-oversize`, `audit-duplication`, `stale-sibling-note`, `leftover-outline-token` and `ac-test-enumeration` entries are added to `metadata.smellWarnings` and never block the merge; see `### Advisory smells` below.
  - **Atomic write**: output file is written under `flock` to prevent partial reads by concurrent processes.
  - **Flags**:
    - `--staging-dir <path>` — directory containing per-story staging `.json` files (default: `.aimi/.tasks-staging/<topic-slug>-<RUN_TS>/`).
    - `--output <path>` — destination `tasks.json` path (default: `.aimi/tasks/<date>-<topic-slug>-tasks.json`).
    - `--split legacy|full-stack` — `legacy` (default) emits one file. `full-stack` picks its split **axis** from the merged array before either writer runs, by counting distinct normalized `.project` values (trim whitespace, strip one trailing slash, blank/absent treated as null):
      - **2 or more distinct values → PROJECT axis** (multi-repo). One output file per distinct project, N files, no frontend/backend decision at all. Project-less stories route to the `"."` root group. Groups are ordered lexicographically by normalized project path; ids are reassigned `US-001..US-M` in contiguous per-group blocks so they stay unique across the whole set. Each file carries `metadata.splitGroup` = `{project, index, total, siblings[], after[]?}` and its own derived `branchName`; `after[]` is optional, ordering only and written on this axis alone: the sorted sibling paths (the strings `siblings[]` carries) of the repositories whose stories this file's stories lost a `dependsOn` edge to, `foundationEdge` drops included, and absent when no edge was dropped. A cycle between files in `after` (A follows B and B follows A through different stories) refuses the merge with exit 1 naming the files, before any write and with the staging directory kept. Output basenames are slugified (every character outside `[A-Za-z0-9_-]` becomes `-`), and two projects that collide on the same slug hard-fail the merge before any file is written.
      - **Fewer than 2 distinct values → SIDE axis** (single-repo/monorepo, including "no story has `.project`" and "every story shares exactly one project"). The unchanged two-file frontend/backend writer; each story is classified by its own file-pattern/title heuristic verdict.
    - `--agent-mode` — demotes Phase 3.1 and Phase 4.1 hard rejects to warnings, allowing CI pipelines to proceed without a user review gate.
    - `--phase-aware` — only meaningful with `--split full-stack`. Strips one trailing `-tasks` segment from the `--output` basename before the writer appends its per-file suffix, so a phase-scoped output path (`<feature>-phase-<N>-tasks.json`) produces single-`tasks`-segment split basenames instead of the legacy double-`tasks` form. The strip is pure basename manipulation performed before the axis writer runs, so it is independent of the axis and composes at any N: on the SIDE axis it yields `<feature>-phase-<N>-frontend-tasks.json`/`-backend-tasks.json`, on the PROJECT axis `<feature>-phase-<N>-<project-slug>-tasks.json` per project. Omitted (default): unchanged legacy derivation.
    - `--foundation <NN>` / `--foundation <project>:NN`, **repeatable** — deterministic dependsOn injection for the Greenfield Foundation Gate, scoped **per project group**. `NN` is the two-digit staged FILENAME idx, resolved against the same `outline_map` the `outline:NN` remap uses (computed once, so the two cannot resolve an idx differently). It is not a position in the merged array: an idx whose file was skipped is reported as `not present among staging files`, and the idx of a file that exists is never shifted by a skipped one before it. Each accepted foundation's assigned `US-NNN` id is appended to the `dependsOn` of every other story sharing **its own** `group_key(.project)` — the identical routing key the axis decision and the PROJECT writer group by (`"."` for the root repository, `null` for an untagged story) — deduplicated (a story that already references its group's foundation, e.g. via its own `outline:NN` token, keeps exactly one occurrence); each foundation's own `dependsOn` stays `[]`. **A normalized project group that no value names receives no injected edge at all** — a normal, silent outcome, whether it has no foundation story or its own Foundation Gate resolved Skip, never a partial failure. Runs after the `outline:NN` remap and before both cycle detection and wave computation, so injected edges participate in both. Composes with `--split full-stack`/`--phase-aware` (the sweep runs once against the full merged array before the split/legacy write branch).
      - **The flag surface is bare-for-one, qualified-for-many.** A bare `NN` is accepted whenever it is the SOLE occurrence, whatever project it resolves to — golden's `proj-fundacao-edge` is a lone bare index resolving to a tagged, non-root project, so a bare-means-root rule would be wrong. Two or more values require EVERY one of them to use the qualified `<project>:NN` form; a bare value alongside another is refused before any index is resolved, because nothing says which project it is for. The qualifier is a **checksum, not a second source of truth**: routing always comes from the resolved story's own `.project` via `group_key`, and the stated project is only ever compared against it. A mismatch aborts the merge before any write, naming the stated project, the actual one and the offending story id — the one divergence between `/aimi:plan`'s Phase 3e text and `story_merge` that nothing else in the pipeline catches. `aimi-cli.sh`'s wrapper validates SHAPE only, one value at a time, and forwards one `--foundation` argument per collected value in argv order; the arity rule and the checksum are staging-file-dependent and belong to `story_merge.py`.
      - **Four refusals, each batched across every named value before the merge dies** (mirroring `resolve_axis`'s batch-then-refuse shape, one complete line per offender and no header, so a single offender prints byte-identically to the pre-batch message): an index present among no staging file, a resolved foundation whose own `dependsOn` is non-empty, a qualifier disagreeing with the resolved story's actual project, and two values landing in the SAME group (an untagged group prints `(untagged)`). An identical repeated value is idempotent, not a collision.
      - **The SIDE axis and legacy mode are unaffected by construction, not by a special case.** `group_key(None)` is one value for every untagged story, so "inject only within your own group" reduces to "inject into every other story" whenever every story shares one group — exactly `resolve_axis`'s own SIDE boundary. No axis-specific branch exists in `inject_foundation`. The SIDE writer emits no `foundationEdge` field.
      - On the PROJECT axis the FULL SET of resolved foundation ids is threaded into the writer (never one scalar — with one foundation per group a single id cannot express "this dropped edge targets *some* group's foundation"). Omitted (default): no injection, byte-identical to pre-flag behavior.

### `apply-audit-patches` and the story-merge audit gate

Two halves of one contract, both consumed by `/aimi:plan` and not invoked by users: the verb is the only sanctioned way to change a staged story after the cross-story auditor has run, and the gate is what makes "the audit ran" checkable when the stories are merged. The command text lives in `commands/references/plan/phase-3d5-audit-apply-gate.md` and `phase-3e-story-merge.md`. Every name and figure below was read off the tree as it stands in release 1.152.0 (the guard-rail, path and `AIMI_ROOT` work of #168 and #169); the release names where the reading was taken and is not a promise that a later edit left it alone, so re-read `scripts/audit_patches.py` and `require_audit` in `scripts/story_merge.py` rather than trusting a name or a number here.

- **`apply-audit-patches --staging-dir <dir> [--result <path>] [--annotate-deferred --reason <text>]`** — `--result` defaults to `<dir>/audit-result.json`. Apply mode validates every patch in that file, applies the survivors with exactly one read and one atomic write per affected staged story, then rewrites the result with `auditedIdx` (the staged idx set, sorted), `appliedAt` and `changedFields`, and prints `{applied, dropped[], unresolved, capped, auditedIdx}`. `dropped[]` holds `{storyIdx, field, op, reason}` plus `trigger` when the sanitizer matcher fired, and plus `rails` on a `guardRails-out-of-sync` entry only: the ascending list of integer rail indices that patch newly broke, never an index that was already broken and never any rail text. Every string is cut to 64 characters and no entry ever carries a patch value or a `matchValue`; `unresolved` is the count now on disk. `changedFields` is `{idx: sorted field names}` with an entry only for an idx that received at least one applied patch; `story-merge` reads it (see `audit-duplication` under `### Advisory smells`). Every refusal is decided before the first write, writes go to temp files beside their targets and are renamed together with the result file LAST, so a failure leaves the old tree or a tree whose result still says "unaudited".
  - **Exit status.** 0 even when patches were dropped (a dropped patch is a report, not a failure). 1 for an unreadable or non-object result, a `patches`/`unresolved` that is not an array, two staged files sharing one idx, an `NN-*.json` symlink resolving outside the staging directory, or a staged file holding a JSON array.
  - **The rules.** `OPS_FOR_FIELD` in `audit_patches.py` maps each allowed field to the SET of ops it accepts, and an op outside that set drops as `op-field-mismatch`: `dependsOn` takes `add`; `tasks` takes `add`, `replace` and `remove`; `notes` takes `add` and `replace`; `acceptanceCriteria`, `implementation.approach`, `implementation.verify`, `implementation.guardRails` and `gate.prompt` take `replace`; `implementation.files` takes `replace` and `remove`, and `implementation.outputs` takes `add`, `replace` and `remove`. `NEEDS_MATCH_VALUE` lists the `(field, op)` pairs that locate their target by an exact `matchValue` (a `tasks`/`notes`/`acceptanceCriteria`/`verify`/`guardRails` replace, a `tasks` remove, and a `replace` or `remove` of `implementation.files` or `implementation.outputs`); a `remove` carries no `value`. A `matchValue` must equal exactly one `tasks[]`, `acceptanceCriteria[]`, `guardRails[]`, `implementation.files[]` or `implementation.outputs[]` entry or one `notes` paragraph (paragraphs are split on `NOTES_SEPARATOR`), or occur exactly once in the `verify` text; anything else drops as `matchValue-match-count`. A `files` or `outputs` `value` (an `add` or `replace`; a `remove` has none) must pass the shared lexical path rule, `implementation_path_problem` in `tasks.py`, or the patch drops as `bad-path` without echoing the value; the `matchValue` is deliberately not judged by it, so an entry already on disk can still be named in order to be removed. An `outputs` `add` is the one op that may create an absent list, and adding an entry already present drops as `post-validation`; every other op on `files` or `outputs` needs the list to exist. At most 10 patches per story, the rest counted in `capped` (and noted by the one `unresolved` entry this module still appends of its own, `audit cap reached: N additional patches dropped`); `tasks[]` capped at 50; a `dependsOn` value must be an `outline:NN` token naming another staged file and not already present.
  - **A `verify` replace carries its rails with it.** The substitution of `matchValue` by `value` lands in every `guardRails` entry that contains the matched text, so a rewritten assertion and its label move together. The postcondition is no NEW breakage, not that every rail is in sync: `_require_no_new_broken_rails` takes `broken_rail_indices` (`tasks.py`, which cuts the verify with `verify_segments`; called rather than restated) before the patch mutates the story and again after, and drops the patch as `guardRails-out-of-sync` only when the second set holds an index the first did not. That entry names the newly broken indices in `rails`. A rail that was already broken before the patch never causes a drop on its own, so one stale rail cannot discard every patch of its story. A `guardRails` replace is held to the same differential check. The patch also drops as `verify-composition` when the new script can swallow a failing line (`verify_composition_findings`, the rule `validate-staging` and the story-merge refusal also use). All three imports from `tasks` (`broken_rail_indices`, `verify_composition_findings`, `implementation_path_problem`) are function-local, because `tasks` imports `story_merge`, which imports this module.
  - **Drop reasons are a closed vocabulary, and a drop is listed in `dropped[]` ONLY.** It adds no `unresolved` entry: the plan decided that as `specFlow:ImportantQ15`, and the report is where a dropped patch is read. An earlier version appended an `unresolved` entry for a semantic drop; the tests that pinned that were changed with it. The reasons are `not-an-object`, `missing-keys`, `bad-storyIdx`, `field-not-allowed`, `op-field-mismatch`, `value-not-string`, `bad-matchValue`, `bad-dependsOn-token`, `sanitizer:<trigger>`, `matchValue-sanitizer:<trigger>`, `bad-path`, `tasks-cap`, `matchValue-match-count`, `gate-prompt-absent`, `guardRails-out-of-sync`, `verify-composition` and `post-validation`. Each patch is applied to a copy of its story and kept only if the copy still passes the story-shape check, which is what `post-validation` reports.
  - **`--annotate-deferred --reason <text> [--agent-deferral]`** is the other mode. For every staged story an `unresolved` entry names it appends a marker, the finding UNCUT (a 2000-character sanity cap; the 200-character cut now applies only to the `oqDecisions` text) and the batch reason (1000-character cap) to `notes`, so the human reason is in the notes of every annotated story. The marker is `DEFER_MARKER_RESOLVED` (`[audit-deferred: resolved at plan review]`) when a human reason exists, and `DEFER_MARKER` (`[audit-deferred: unresolved — review before execution]`) under **`--agent-deferral`**, which is for a deferral an agent chose with no human reason: it keeps the unresolved marker and adds no reason text, and the wrapper refuses it without `--annotate-deferred`. The verb prints `{annotated, oqDecisions}` with one `{anchor: "auditUnresolved:<idx>", source: "auditGate", text, resolution: "deferred"}` per entry. It is **not idempotent, by design** — the orchestrator calls it once per Defer decision. The wrapper refuses it with an empty `--reason`, and refuses `--reason` without it.
  - **The `audit-failed` stub fans out.** When the result file is the stub (`status` is `audit-failed`), a deferral that covers the `_audit` sentinel annotates EVERY staged story with a note that the cross-story audit did not run (plus the human reason when there is one), while the decision stays a single `auditUnresolved:_audit` entry in `oqDecisions`. Any other `_audit` entry (a malformed auditor entry, the patch-cap notice) is recorded in `oqDecisions` only, annotates no story, and leaves the file as it was. `test_annotate_audit_failed.py` pins both.
- **The sanitizer is a matcher, and it accepts a subset of what `validate-tasks` accepts.** `sanitize_patch_value` in `scripts/sanitize.py` answers yes or no and never rewrites: an auditor's patch is a whole replacement text, and deleting half of it would store something nobody proposed. It refuses only imperative forms — the `PATCH_TRIGGERS` `ignore-previous`, `system-label`, `instructions-heading`, `instructions-label` — never prose that merely names a word. For the one field `validate-tasks` screens, `tasks`, it then applies `SUSPICIOUS`, the validator's own pattern, which is defined once in `sanitize.py` and imported by `tasks.py` along with `VALIDATED_PATCH_FIELDS`; that last trigger is `validator-screen`. So a `tasks` patch the matcher accepts cannot fail `validate-tasks` afterwards. A field the validator never screens gets the narrow rules only. There is no private copy of any pattern in `audit_patches.py`.
  - **Two fields are judged, never rewritten: `VERBATIM_PATCH_FIELDS`.** `implementation.verify` and `implementation.guardRails` hold shell the expander wrote unsanitized, and any rewrite would corrupt it. `judge_patch_value(value, field)` runs the same four narrow rules as `sanitize_patch_value` on the same normalised copy and nothing else (no `$(` removal, no backtick unwrapping, no length cut, no validator screen), and answers `(value, None)` byte for byte or `(None, trigger)`. `audit_patches.py` picks between the two by `field in VERBATIM_PATCH_FIELDS`, for both `value` and `matchValue`.
- **One crossing, no lock.** The verb is modelled on `cmd_story_merge`, not on the tasks.json verbs: there is no tasks file, and the staged files are private to one `/aimi:plan` run. Bash does the flags and the path confinement, then `check_python3`, then one `python3 audit_patches.py` call. Both `--staging-dir` and `--result` arrive as CLI arguments, so `validate_path_in_project` confines them before `python3` starts and an escaping argument is refused without the module running. No path is ever built from an auditor-supplied string: the idx to file map comes from the `[0-9][0-9]-*.json` glob (`staged_idx_map`), which skips symlinks and `*-outline.json`.
- **The gate: `require_audit` in `story_merge.py`.** With fewer than two staged files nothing is checked. With two or more, `story-merge` refuses unless `audit-result.json` exists, parses, is an object with `patches[]`, `unresolved[]` and `auditedIdx[]` (strings), every staged file is named `NN-<slug>.json`, and the sorted set of `auditedIdx` equals the staged idx set. The staged set comes from the same `staged_idx_map` the verb audited against, so the two cannot disagree on which files are stories. The refusal reads `Error: story-merge: staging directory <dir> was not cross-story audited (<reason>). Run the cross-story audit … and retry.` and prints at most 50 idx tokens, with anything that is not a two-digit string shown as `?`, because that list was written by a model.
- **The `audit-failed` stub passes, loudly.** When the auditor crashes, `/aimi:plan`'s Failure Fallback writes `{"status":"audit-failed","auditedIdx":[…],"patches":[],"unresolved":[{"storyIdx":"_audit",…}]}` with `auditedIdx` taken from the same glob. The gate accepts it, and a merge that completes prints `AUDIT_FAILED_NOTICE` once on stderr (`… the cross-story audit failed for this staging directory; plan shipped unaudited`); a refused merge prints no such line. Step 5 of `/aimi:plan` matches on the phrase inside that constant, which is why it is a constant.
- **There is no escape flag, deliberately.** No flag, no environment variable and no `--agent-mode` exemption: an escape hatch is a default-off gate by another name. `test_story_merge_call_carries_no_gate_escape` in `test_plan_wiring.py` pins that the `/aimi:plan` call carries none.
- **What it does not do.** It proves the audit step ran, or was recorded as failed; it does not judge what the audit found, and a stub naming every idx passes. It does not catch a staged file edited after the audit by a route the staging guard cannot see (see `### Staging-file guard`).
- **Version skew for readers.** `commands/plan.md` now depends on this verb. A plugin CLI installed before the verb existed has no `apply-audit-patches`, so until the plugin is updated (the Claude Code cache, or a re-run of `install.sh --to opencode`) a plan run against that older CLI cannot apply patches, and a multi-story `story-merge` there does not gate. Probe a checkout's own `scripts/aimi-cli.sh` rather than the resolved CLI when you test this.

### `validate-outline`, `validate-staging` and `outline-shift`

Three verbs that give `/aimi:plan`'s expansion phases a deterministic check where they used to rely on prose. None takes a tasks file, so none takes a lock; each follows `cmd_apply_audit_patches`'s shape: bash parses the flags, confines every path argument with `validate_path_in_project` before `python3` starts (an escaping argument is refused without the module running), calls `check_python3` and **refuses** rather than degrading, then makes one crossing. They refuse on a missing interpreter because a verb that answered "valid", `{}` or "nothing to do" without one would turn a missing dependency into a passing check. `validate-outline` and `outline-shift` are in `scripts/outline_contract.py`, the pure-logic module of the planning verbs; `validate-staging` is in `scripts/story_merge.py`, beside the story-merge refusal that shares its rule.

- **`validate-outline --outline <path>`** — Checks the `produces`/`consumes` contract on the outline's entries and derives the expansion waves. A token is `[ext:]<kind>:<name>`, `<kind>` one of `sym`, `path`, `cli`, `http`. The name is judged by `roadmap.py`'s `_identity_reasons` (imported, never mirrored, so the two cannot disagree on what an identity is) plus a per-kind rule: a non-`http` name holds no whitespace, an `http` name is exactly `METHOD /path`, a `path` name has no leading slash and no `..` segment. `ext:` is accepted only in `consumes` and marks a name that already exists in the repository, so it needs no in-plan producer. An entry carrying neither key is valid, and an outline with no declarations yields one wave holding every idx. Prints `{valid, errors, waves, edges, counts}`: `errors` is `[{code, idx, message}]` with `code` one of `bad-idx`, `duplicate-idx`, `bad-contract`, `bad-token`, `duplicate-produces`, `unproduced-consume`, `self-consume`, `external-also-produced`, `cycle`; `waves` is a Kahn layering over producer-to-consumer edges (each wave sorted by idx, `[]` when invalid); `edges` is `[{from, to, name}]`. Exit 0 for a valid outline and 1 for an invalid one, with the object still printed; an unreadable argument refuses on stderr with nothing on stdout. `/aimi:plan` runs it when the outline is written, after every outline-gate edit (Approve is refused while an error stands) and again before Phase 3d, where `waves` is the dispatch order: expanders run wave by wave, at most 8 at once, each consumer handed a data-wrapped slice of its producers' validated staged stories.
- **`validate-staging --staging-dir <dir> [--outline <path>]`** — Reports the staged `NN-*.json` stories that cannot be merged as written, as `{idx: [finding, ...]}`, exit 1 when non-empty and 0 with `{}` when clean. Files come from `audit_patches.staged_idx_map`, the glob the audit gate uses, and a file that is not valid JSON is skipped rather than fatal (its shape is Schema Validation's business). Each staged story is judged by four rules and, with `--outline`, a fifth, and the findings of one idx come out in that order. First the verify-composition rule, `verify_composition_findings` in `tasks.py`: a multi-line `implementation.verify` runs as one script and exits with its LAST command's status, so a failing earlier line is swallowed unless the script starts with `set -e` (or `-o errexit`) and never switches it off, or chains every later line with `&&`/`||`. Second the guard-rail rule, `guard_rail_findings`: every `implementation.guardRails` entry must be the exact text of one top-level segment of the story's own `verify` (the segments `verify_segments` cuts), and a finding names `implementation.guardRails[<i>]`, says what larger construct a rail sits inside when it does (function, loop, if/case block, group, subshell, heredoc) and gives the remedy. Third the path rule, `implementation_path_findings`: an `implementation.files` entry must stay inside the story's repository (not absolute, not `~`-led, no `..`, `.` or whitespace or backslash in it), and an `implementation.outputs` entry must additionally start with `.aimi/` followed by a path; a `files` entry that leaves the repository gets the remedy that points at `implementation.outputs`. Fourth the url rule, `verification_url_findings` in `tasks.py`: a `verification.url` that is a non-empty string must match the R15 charset (`URL_CHARSET`), so a method-prefixed `POST /api/x` (its space is outside the charset) is reported as `verification.url "<url>" contains characters outside the allowed charset`, keyed by idx; an absent `verification`, or a null, empty or non-string url, reports nothing. `validate-tasks` R15 builds its error from the same sentence builder (`<tasks_file>: <id> <finding>`), so the two cannot word it differently, and `story-merge` does NOT refuse it: a staged story with a rejected url still merges and `validate-tasks` R15 stays the last gate. The last applies with `--outline`: every producer-to-consumer edge `validate-outline` reports requires `outline:<from>` in the `dependsOn` of the story staged as `<to>`. `/aimi:plan` runs it as step 2b of Schema Validation and feeds a finding into the retry loop. The url finding is wrapped by `verification_url_findings_sanitized` in `story_merge.py`, whose `tasks` import is function-local. The rail and path findings are built by `rail_and_path_findings` in `story_merge.py`, which passes each through `rm_sanitize` at 500 characters because they quote model-written text; `validate-staging` and the story-merge refusal both read it, so the two cannot disagree about a story.
  - **The verify rule exists at three places and they share one function.** `validate-tasks` rule **R23** reports it as a WARNING (never an error, so an existing plan is never refused for it; R23 also warns on a `grep` aimed at a directory with no `-r`, which exits 2 and which a leading `!` turns into a pass). `validate-staging` reports it during expansion. `story-merge` REFUSES it, ahead of every remap and sweep, with no `--agent-mode` exemption: an audit patch can introduce the verify after the expansion-time check has run. An `apply-audit-patches` replace of a `verify` that would trip it is dropped as `verify-composition`. The finding quotes model-written text, so `story_merge.py` passes it through `rm_sanitize` before it reaches stdout or stderr.
  - **The rail and path rules are shared the same way, between four callers.** `validate-staging` reports them during expansion, `story-merge` refuses them, `apply-audit-patches` drops a patch that would newly break a rail (`guardRails-out-of-sync`) or write a path value the rule refuses (`bad-path`), and `validate-tasks` carries the path half as two rules of its own, one a warning and one an error; the Tasks File Schema block names them. The rule text lives once in `tasks.py` (`guard_rail_findings`, `broken_rail_indices`, `implementation_path_problem`, `implementation_path_findings`) and every caller imports it inside a function body.
- **`outline-shift --staging-dir <dir> --old <path> --new <path>`** — Run when the outline is edited AFTER stories were expanded, so a gate edit does not cost a full re-expansion. Entries are matched by exact title (two sharing a title pair up in idx order); `plan_shift` decides the whole shift in memory, then `apply_shift` renames the shifted `NN-<slug>.json` files and rewrites their `outline:NN` tokens in one pass through the same `OUTLINE_TOKEN` pattern `story-merge` uses. A removed entry's file is deleted, a validation stamp (`NN-<slug>.json.validated`) beside a renamed or removed story file is renamed or deleted with it, and so is `audit-result.json` whenever anything changed (the audit described a numbering that no longer exists). Prints `{renamed[{from,to,file}], removed[], reexpand[{idx,reason}], expand[], auditInvalidated}`: `renamed[].from` and `removed[]` are OLD idx, every other idx is NEW. A kept story is listed in `reexpand` only when the edit really affects it: it cites a removed entry, its own `produces`/`consumes` changed, or it consumes a name whose producer was removed, changed what it produces or is new. A new entry is in `expand`. Nothing is written until every refusal is decided; files move in two phases so a chain of renames cannot collide, and a failure before the deletions puts every moved file back. `outline_contract.py` takes `staged_idx_map` and `OUTLINE_TOKEN` with a function-level import and never imports `tasks`, `story_merge` or `audit_patches` at module level, so the contract module stays out of the `tasks` to `story_merge` to `audit_patches` import chain. The command side is the interactive-only `Edit outline` option at the Failure Budget and the Unresolved Gate (`commands/references/plan/phase-3c-outline-gate.md`).
- **Version skew.** A plugin CLI installed before these verbs existed has none of them, so a `/aimi:plan` run from this tree against that CLI fails at its first call to one. Probe a checkout's own `scripts/aimi-cli.sh`, as for `apply-audit-patches`.

### `plan_checks.py` and its backtest

`scripts/plan_checks.py` holds pure static checks over plan text and writes, spawns and runs nothing. It has four verify detectors in a `DETECTORS` tuple (`pipefail-grep-q`, `runner-summary-colour`, `git-diff-unstaged`, `negated-grep-no-twin`) plus `citation_drift` and `reverse_references`. Its tests are `scripts/tests/test_plan_checks.py`. The backtest is `scripts/tests/backtest_known_gaps.py` (tests in `test_backtest_known_gaps.py`): it links each file in `.aimi/known-gaps/` to a story by filename alone, scores every check, and prints a SHIP or NOT-SHIP verdict per check, as aggregate counts only. Run `python3 plugins/aimi-engineering/scripts/tests/backtest_known_gaps.py` for the table and the same command with `--check` as the gate (exit 0 when the corpus is absent, exit 1 when the computed verdicts differ from the recorded ones).

- **The recorded run (as of 2026-10-26, 29 of 157 gaps linked to a story).** `BACKTEST_VERDICT` is `(pipefail-grep-q, git-diff-unstaged)`. NOT-SHIP: `runner-summary-colour`, `negated-grep-no-twin`, `citation_drift` (no hit on a linked gap story) and `reverse_references` (28 hits, but it flags 396 of 408 stories that had no gap). The `git-diff-unstaged` SHIP rests on one linked hit. Re-run rather than quote.
- **`check-citations` and rule R25 are not shipped.** They would have run `citation_drift` and `reverse_references`, which the backtest withheld, so neither exists in `aimi-cli.sh` or `tasks.py` and the `validate-tasks` rules end at R24. The two functions stay in the module as available code that no verb calls; if a later backtest ships either, the verb or rule goes beside `get-story-context`'s neighbours or R24 and this paragraph changes with it.

### `split-detect`

`split-detect` (the read side of `metadata.splitGroup`; its usage text in `aimi-cli.sh` is the contract) answers `{mode, anchor, members, activeCount, total, degradedReason}`; every member record carries `after[]`, the member paths that file must follow (`metadata.splitGroup.after[]` resolved by basename against the anchor's directory like `siblings`, empty when the marker has none, names a file outside the group, or the scope is not a marked project split). Two additions in 1.154.0:

- **Mode `ambiguous`.** In flat scope, a newest flat plan with no pending or in-progress story and at least one failed story still reads as active, so it used to win over a roadmap phase waiting to be claimed. When `roadmap.py planned-phases` finds a claimable planned phase, the mode is `ambiguous` and the object adds `failedCount` and `claimablePhases`, so the caller asks instead of guessing. The roadmap crossing happens at most once; with no `python3` it degrades to the old answer with one hint on stderr.
- **`--dir <d> --include-completed`.** Without it a group whose stories are all completed is dropped, so Phase Completion could not list a finished phase's members. With it the group is kept; it requires `--dir`. On a non-git `AIMI_ROOT` an empty membership is refused with exit 1, because the caller would otherwise fall back to `.` as a git target. The four Phase Completion steps use it.

### `check-version` and the global cli-path pointer

`check-version` used to compare only the PROJECT pointer (`.aimi/cli-path`) against the newest install, and treated the machine-wide pointer (`~/.config/aimi/cli-path`, or `$AIMI_CONFIG_DIR/cli-path`) as something to overwrite once the project pointer was found stale. A project whose own pointer was `current` or absent therefore never looked at the global one, so a session in any other project kept resolving an older install, or one under a second Claude config root. `_check_version_global_pointer` now compares it too, and the JSON gains a `globalCli` object `{status: "stale"|"fixed", storedVersion, latestVersion, storedPath, latestPath}` (with `reason` when a repair is declined). When the project pointer is `current` or `missing`, the top-level `status`, `storedVersion` and `latestVersion` are the global pointer's; when the project pointer is itself `stale` or `fixed`, its own JSON is unchanged and `globalCli` sits beside it. Without `--fix` a stale global pointer exits 1.

- **`--fix` writes only after the target survives four checks** (it exists, is executable, is named `aimi-cli.sh` and sits under an `x.y.z` version directory) and reports `fixed` only after re-reading the pointer, because `write_global_cli_cache` declines a `/.worktrees/` path as a no-op success. A repair it cannot confirm leaves `globalCli.status` at `stale` with a `reason`, at exit 0.
- **Nothing is reported or written** when the pointer is current, missing, empty, legacy-file-only or not a versioned plugin-cache path, and never under `AIMI_DEV_DIR`, the converter branch, a valid `AIMI_CLI_PINNED` or a directory-source install. The legacy `~/.claude/aimi-engineering-cli-path` is a read fallback only and is **not repaired**.
- **Known remaining gap.** When the PROJECT pointer is stale and `--fix` runs, the older project-fixed branch still writes the global pointer through the unvalidated `write_global_cli_cache` path rather than through the four checks above. The user-facing contract is in `commands/references/cli-path-resolution.md`; `scripts/tests/test_version_cache.py` pins the verb.

### `slugify`

`aimi-cli.sh slugify (--stdin | <text>)` prints an ASCII directory slug and is the deterministic form of `commands/references/topic-slug.md`'s five steps, for a caller that names a directory after the result. It is dispatched ahead of `find_aimi_root`, so it answers from any directory, takes no tasks file and no lock, and passes the text straight to `scripts/slug.py` as one argument or as stdin bytes, never through a shell. It calls `check_python3` and **refuses rather than degrades**: a slug built without the interpreter would be a different slug. The text is decomposed with NFKD and only its ASCII characters are kept, then lowercased, runs of non-alphanumerics become one hyphen, the ends are trimmed and the result is cut to 50 characters and trimmed again. **NFKD only:** a letter with no decomposition (o with stroke, sharp s, the ae ligature) is dropped, not transliterated, so `Søren Straße Ærø` gives `sren-strae-r`. Text with no ASCII letter or digit left is refused with exit 1 and nothing on stdout. `ascii_fold` in `slug.py` is also what `bundle_relevance.py` folds with. Tests: `scripts/tests/test_slug.py` and the `slugify` cases in part 2 of `test-aimi-cli.sh`.

### `detect-design-bundle --feature-stdin`

A stray or placeholder bundle left in the tree carries the same README marker as the real one, so a scan used to elect it or tie and refuse. `--feature-stdin` reads the feature description from stdin (never an argument) and hands it, with the scan-tier candidates as argv, to `scripts/bundle_relevance.py`, which keeps a candidate only when its directory name or the first H1 of its `project/BusinessSpec.md` shares at least one token with the description. Tokens are `ascii_fold`ed runs of `[a-z0-9]` of at least 3 characters minus English and Portuguese stop-words and a short list of generic app words, and the description is capped at 2000 characters before folding. Zero relevant bundles prints `null`, one prints that bundle, and two or more refuse with exit 3 listing only the relevant ones; the discarded paths go to stderr and into a `filtered[]` array on the JSON object outputs. A description with no token left (empty, whitespace, only stop-words) turns the filter off and adds no `filtered` key. The phase tier, `--bundle` and `--all` are never filtered, and without the flag every output is unchanged. It requires `python3` and refuses with exit 1 without it. Tests: `scripts/tests/test_bundle_relevance.py` and the `--feature-stdin` cases in part 3 of `test-aimi-cli.sh`.

### Advisory smells

Six entry types `story-merge` can add to `metadata.smellWarnings` (see the Tasks File Schema block for their shapes), alongside `orphan-symbol` and `verify-coverage`: `field-overlap`, `story-oversize`, `audit-duplication`, `stale-sibling-note`, `leftover-outline-token` and `ac-test-enumeration`. All six are **advisory**: they print one stderr banner per type with one line per story, and never drop a story, block the merge or change its exit status. They are computed inside each writer (legacy, SIDE, PROJECT) AFTER the id remap, so `storyId` is the id that lands on disk, and over the union of every output file of a split, so the median is plan-wide. On a split the array is written to every file. `advisory_story_smells` returns them in the order listed.

- **`field-overlap`** measures how much of `tasks[]` restates `implementation.approach`: the share of `tasks[]` word 4-grams (built per entry, so none spans two) that also occur in the approach. Knobs in `scripts/story_merge.py`: `FIELD_OVERLAP_NGRAM` 4, `FIELD_OVERLAP_THRESHOLD` 0.30, `FIELD_OVERLAP_MIN_TASKS` 3, `FIELD_OVERLAP_MIN_APPROACH_CHARS` 200. A story under either minimum, or with no n-gram, is not eligible and gets no entry.
- **`story-oversize`** measures a story's serialized size as it lands on disk, minus `wave`, compact separators, UTF-8. It fires above `STORY_OVERSIZE_FLOOR_BYTES` (**12288**), or when the plan has at least `STORY_OVERSIZE_MEDIAN_MIN_STORIES` (3) stories and the story is above `STORY_OVERSIZE_MEDIAN_FACTOR` (2) times the plan median and above `STORY_OVERSIZE_MEDIAN_MIN_BYTES` (4096). The entry carries `bytes`, `medianBytes` and `floorBytes`. The story expander's own aim is 6 to 8 KB, so the floor sits well above the aim on purpose.
- **`audit-duplication`** asks the `field-overlap` question of one narrower population: a story an audit patch changed in BOTH `tasks` and `implementation.approach`. It reads `changedFields` from `audit-result.json` (written by `apply-audit-patches`) through `read_changed_fields`, the one tolerant reader: a missing file, an unparseable one or a value of the wrong shape answers `{}` and says nothing, because the only consumer is an advisory smell. The record is keyed by staged filename idx and attached to each story as the `_auditChanged` working key, which is stripped from output. It fires when `field_overlap_ratio` reaches `AUDIT_DUPLICATION_THRESHOLD` (0.20, below the 0.30 of `field-overlap` because the prior that the overlap is the audit's doing is stronger for a story an audit changed). `AUDIT_DUPLICATION_FIELDS` names the two fields. A merge with no audit record, or a record naming only one of the two, yields nothing.
- **`stale-sibling-note`** scans every `notes` paragraph before the last `NOTES_SEPARATOR` (the final one is what an audit appended, and a note with no separator is never scanned) for a citation matching `STALE_NOTE_SIBLING_PATTERN` (`US-NNN`, or the prose `story N`). It counts only a citation of a story that exists in this plan and is not the story carrying the note. The entry carries `cited` (sorted ids).
- **`leftover-outline-token`** fires when `LEFTOVER_OUTLINE_PATTERN` (`outline:` plus one or more digits) survives in any string field except `dependsOn`, working keys and `_`-prefixed keys. `OUTLINE_TOKEN` owns exactly two digits not followed by a third, so `outline:7` and `outline:041` are text the remap leaves alone and this reports. The entry carries `fields` (sorted field paths).
- **`ac-test-enumeration`** fires per acceptance criterion naming `AC_TEST_ENUMERATION_MIN` (3) or more distinct `test_*` identifiers (`AC_TEST_ENUMERATION_PATTERN`); coverage belongs in `tasks[]`. The entry carries `index` and `count`.
- **The thresholds are knobs with an as-of marker, not facts.** `SMELL_CALIBRATION_AS_OF` is `"9fcfa44 2026-10-23"`, and the comment above the constants records what firing counts were measured as of that commit: zero of all six types on the golden corpus (86 staged cases, 167 stories), and on the #164 plan exactly `leftover-outline-token` (5 stories, 11 fields; that plan predates the text remap). `python3 scripts/tests/calibrate_story_smells.py` prints the tables and `--check` exits 1 when a constant fires on any golden case or when the set of types firing on that plan is not exactly that one (`EXPECTED_REFERENCE_TYPES`). Change a constant only within what the script prints, and update the marker and the counts in the same commit. Know what 12288 means before relying on it: measured over every tasks file then under `.aimi/`, it would flag about half of the stories ever written (the comment gives 210 of 433), because it was set from one plan's maximum, not from history. It is a prompt to look, not a verdict.
- **None of the six gates completion.** `roadmap.py` reads only `verify-coverage` entries (`_unacknowledged_verify_coverage`), and `grep` finds none of these names in `roadmap.py` or `tasks.py`. `acknowledge-smell` matches on `storyId` + `type` for any type string, so it can record an acknowledgement on them, but that is **record-only**: nothing reads the flag for them, and a re-merge regenerates the array and resets it. All six are proxies — shared wording is not proof a field is redundant, a pattern is not proof a reference is stale, and bytes are not proof a story is badly bounded — which is why they inform rather than gate; see `commands/references/context-budget.md` § The Question Every New Gate Must Answer before promoting any of them to a gate.

## aimi-cli.sh Roadmap Lifecycle Subcommands

Seventeen CLI subcommands manage the phase/milestone roadmap layer for large-scope features (see `commands/references/scope-contexts.md` for when a feature qualifies for phases vs. the flat single-scope-context pipeline). All are internal — consumed by `/aimi:brainstorm`, `/aimi:plan`, `/aimi:execute`, and `/aimi:status`, not invoked by users directly.

**One verb outside this list reads `roadmap.json` too, and it is `list-archivable`.** It is a `tasks.json` verb — it decides which task files a feature has finished with — but a feature folder's phase files surface as a unit only when the feature's own `roadmap.json` marks every phase completed, so it opens one roadmap per feature folder it finds. That read is `roadmap.py`'s `list-archivable-phases --roadmap <path>` op: path-shaped like `op_roadmap_eligible` rather than slug-shaped like the wrapper `cmd_roadmap_eligible`, because `list-archivable` walks whatever roadmaps it discovers and has no feature slug to give. It follows `roadmap-eligible`'s general form — a verdict for **every** phase, `{id, status, terminal, stuck}`, plus `nonTerminalCount` and `stuckIds` (the stuck ids already joined into the exact `, `-separated string the warning prints, so bash never re-implements `(.id|tostring)`) — and adds `usable`, because a roadmap.json this verb cannot read is a normal outcome that INCLUDES the feature anyway, where `read_doc` would `die()`. `terminal` is `status in TERMINAL_PHASE_STATUSES` — `completed` and `cancelled` both count, reused from story 01's constant rather than re-literalled — so a feature whose only non-completed phase is cancelled is included exactly as one that finished cleanly, and `nonTerminalCount` excludes a cancelled phase the same way. It reads no tasks file (`list-archivable` has already read those itself) and it is **ungated by `_roadmap_require_contracts`**, for the same reason `roadmap-eligible` is: it touches only `.phases[].status`, never a `creates`/`needs` entry. It is not a CLI subcommand — nothing dispatches `list-archivable-phases`; it is the one op in `roadmap.py` reached from outside the `roadmap-*` family, which is why `_VERB_FOR_OP` names `list-archivable` as the verb its diagnostics should point at.

**`python3` is a runtime requirement for these verbs, not only a test-time one.** Sixteen of the seventeen shell out to `scripts/roadmap.py`, which owns `roadmap.json`'s document logic; each calls `check_python3()` first and fails with an install hint when it is absent. `estimate-payload` is the one roadmap verb that shells out to nothing and stays pure Bash + jq. **Outside this group the requirement is no longer narrow** — `story-merge` needs it, so does every `tasks.json` verb, including the per-story hot path `/aimi:execute` runs (`mark-*`, `list-ready`, `next-story`, `count-pending`, `get-story-context`), and so does the whole `models.json` surface, where `detect-models` refuses and the four readers degrade instead. Do not read this section as the boundary of the dependency; the normative statement, its full scope, which verbs degrade rather than refuse, and what it means for an OpenCode install are in the top-level `CLAUDE.md` § Testing, and stating it twice is how the two drifted before.

- **`roadmap-init --feature <slug> [--file <path>] [--sync] [--brainstorm-path <path>] [--integration-branch <name>]`** — Materializes `roadmap.json` from a phases array (stdin or `--file`). `--sync` merges additively into an existing roadmap instead of erroring on an existing file. A `creates`/`needs` entry is `{identity, description}`; one carrying any other key, or a malformed identity, is refused here at write time — the identity/description contract and its diagnostics are documented once, in `commands/references/scope-contexts.md` § Creates/Needs Contracts. Refuses a pre-`2.0` roadmap under `--sync`, naming `normalize-contracts`, rather than merging the two entry shapes into one document. `--integration-branch` declares the feature-level integration branch a rolling-wave roadmap's first phase should open its PR against (issue #87's direction 1). **No command passes it** — it is a human affordance, the same shape `roadmap-amend-phase` is for correcting a phase, and issue #87 direction 1 documents hand-editing `roadmap.json` as the supported route. `/aimi:plan` briefly parsed the value out of brainstorm frontmatter and threaded it here; nothing ever wrote that frontmatter key, and the parse interpolated LLM-authored text into an executed bash line, so it was removed rather than given a producer — validated against the same branch pattern `roadmap-amend-phase --branch` already enforces on a phase, in `init-validate` — i.e. before the lock and before `mkdir -p`, so a refusal creates no feature directory and no stale `.lock` (`init-write` re-checks it, two layers on purpose). It is read only when materializing a fresh `roadmap.json`; an additive `--sync` call preserves whatever value (if any) is already on disk and never overwrites it from this flag, since the field is meant to be addable to an existing roadmap by hand.
  - **Sanitize reporting (D10/D11):** every free-text field it sanitizes — `name` 200, `goal` 2000, `slug` 100, `notes` 5000, each `successCriteria` entry 2000, each `areas` entry 500, `branch` 200 — and each `creates`/`needs` entry's `description` (500) is classified by `sanitize.py`'s `rm_sanitize_report(value, maxlen)`, which calls `rm_sanitize` itself twice (unclamped, then at the cap) rather than re-deriving any of its regexes. A field the sanitizer actually rewrote or truncated draws one stderr warning line — naming the phase, the field, the list index when the field is a list entry, the change kind(s) (`rewritten`/`truncated`, both possible together) and before/after character counts, **never the field's own value, before or after** — and the result JSON's `sanitized[]` array carries the same per-field records, `{phase, field, index, changes[], before, after}`, empty when nothing changed. `--sync`'s anti-clobber applies here too: a phase left untouched reports nothing, the same as it adds nothing to `added`. Both channels are populated only once the write has landed, so a refused call reports nothing because nothing was written.
- **`roadmap-amend-phase --feature <slug> --phase <id> [--goal <text>] [--branch <name>] [--name <text>] [--slug <slug>] [--file <path>] [--retarget-needs "<old>=<new>"]...`** — Corrects an **existing** phase's contract in place, under the same `flock` + `mktemp`-then-`mv` discipline `roadmap-init` uses. This is the verb `guard-runtime-state.py` points at when it blocks a Write/Edit on `roadmap.json`; before it existed, that redirect named nothing. Amendable fields are `goal`, `successCriteria`, `creates`, `needs`, `areas`, `branch`, `name`, `slug` — supplied as scalar flags or as a JSON object on stdin/`--file` (stdin is read only when no scalar flag is given). The merge is **partial by key presence**: a key present replaces that field wholesale, a key absent leaves the stored value byte-for-byte unchanged, as do every other phase and the document metadata — except `dir`, which is never itself a patch key but is **recomputed** from `id` and the (possibly amended) `slug`, using the exact `phase-<id>[-<slug>]` formula `roadmap-init`'s own `init_sanitize` applies, whenever `name` or `slug` is amended.
  - **`branch` is amendable** because nothing else writes it for an existing phase: `roadmap-init` sets it once at creation and `--sync`'s anti-clobber guarantee never revisits it — which is exactly why a decimal phase's `null` branch could not be filled in. Amending it rewrites the roadmap field only; it does not move a worktree or git branch an `in_progress` phase already created.
  - **`status` and `claim` are not amendable** on the opposite ground: `roadmap-set-status` already owns status (transition graph plus the `handoff.md` precondition) and `roadmap-claim`/`roadmap-release-claim` already own claims (PID liveness, self-reclaim). A second writer would duplicate those guarantees, so both keys are rejected by name pointing at their owner. `id` and `dependsOn` are phase identity with no writer at all and are rejected by name too; `dir` is refused with its own distinct message naming `slug` as the way to change it, rather than folding into that generic phase-identity message.
  - **`name` and `slug` are amendable, and the one pair here whose amendment is gated on more than its own shape.** Renaming a phase's identity can move a directory and rewrite another document (its own tasks file), so amending either is refused — by name, before `roadmap.json` or any file on disk is touched — unless the phase's own `status` is `pending` or `planned`, its `claim` is `null`, and every story in its own phase tasks file (resolved via `_phase_tasks_path`, when that file exists) is still `pending`. When the guard passes and the amended `slug` changes the computed `dir`, the same locked call also: validates the new `dir` against `DIR_REGEX` and against a collision with another phase's stored `dir` or an existing filesystem path (refusing before anything moves or writes); moves `<feature_dir>/<old_dir>` to `<feature_dir>/<new_dir>` on disk when that directory exists; rewrites that phase's own tasks file's `metadata.phase.dir` to the new `dir`; and rewrites `metadata.branchName`'s own `-phase-<idSlug>-<oldSlug>` segment to the new slug when it was present (the token `commands/references/plan/phase-4-metadata-identity.md`'s `branchName` rule composes). A phase whose directory exists but carries no tasks file yet still moves cleanly, with no tasks-file rewrite attempted. If the `roadmap.json` write then fails — the directory and the tasks file's metadata having already changed — the same call moves the directory back and restores the tasks file's metadata to their exact pre-amend values before exiting non-zero, leaving the tree exactly as it was. The result JSON's `move` key is `{from, to}` when a directory was moved, `null` otherwise.
  - Amended values pass `roadmap-init`'s own gates (same sanitizer and caps, same `creates`/`needs` identity guard, same branch pattern). Dropping or renaming a `creates` identity a later phase cites in `needs` is **refused by default**; `--retarget-needs "<old identity>=<new identity>"` (repeatable) authorizes it, and the same locked write then replaces every matching downstream `needs` entry with the amended phase's new `creates` entry verbatim. Identity comparison is exact equality on the entry's own `identity` field, never substring containment. Refuses a pre-`2.0` roadmap, naming `normalize-contracts`. An amendment that would duplicate another phase's `creates` identity is refused (it would produce a roadmap `validate-contracts` rejects) — **except a cancelled phase's own `creates` are exempt from that collision scan**, the same exemption `duplicate_creates()` applies, so a live phase may reuse an identity a cancelled sibling abandoned; a completed phase whose `handoff.md` omits a newly introduced identity only draws a stderr advisory and still writes.
  - **Sanitize reporting** follows `roadmap-init`'s identical shape (see above), over the same caps for whichever of its amendable fields the call actually carries — `name` 200, `goal` 2000, `slug` 100, each `successCriteria` entry 2000, each `areas` entry 500, `branch` 200, each `creates`/`needs` entry's `description` 500. Every entry's `phase` is this call's own `--phase`, since one call amends exactly one phase. Result JSON is `{roadmap, phase, amended[], retargeted[], sanitized[], move}`.
- **`normalize-contracts --feature <slug>`** — Migrates a roadmap's stored `creates`/`needs` entries from the `roadmapVersion` `1.0` form — one string, `"identity (description)"` — to the `2.0` form `{identity, description}`, in place, under the same `flock` + `mktemp`-then-`mv` discipline every other roadmap writer uses. Each identity is computed by the **same function every reader used before the migration**, so no identity changes by a byte and no downstream `needs` is repointed; an entry with no `(` gets `description: ""` (never `null`), and an entry already in object form is left untouched, which is what makes a second run a no-op. It does not judge: a prose or whitespace-bearing identity the current writer would refuse migrates unchanged, and the reader reports it afterwards by name — repairing on the way past would silently change what a phase promises. One-way: an entry whose text after the first `(` does not end in `)` loses that unbalanced trailing paren from its description, which the identity half never sees. Prints `{roadmap, converted, roadmapVersion}`, where `converted` counts entries that were strings *before* the run.
- **`roadmap-get --feature <slug> [--phase <id>] [--next-eligible]`** — Reads a single phase, or the next eligible-to-claim phase, from `roadmap.json`.
- **`roadmap-eligible --feature <slug> [--statuses <a,b>]`** — Prints one JSON object naming **every** phase in roadmap order with a machine-readable verdict — `{id, name, status, claim, eligible, unmet[]}`, each `unmet` entry `{id, status}` — plus `eligible` (the ordered ids of the eligible ones) and `eligibleCount`, so one call serves both a list rendering and a by-id lookup. Structured fields only: no field carries a sentence, because user-facing wording follows the reader's own language (`commands/references/user-communication.md`) and the calling command composes it. **Zero eligible exits 0** with an empty list — unlike `roadmap-get --next-eligible`, which exits 1 — so a command substitution can tell "no phase ready" apart from a broken CLI. `--statuses` defaults to `pending,planned` and refuses an unknown name instead of silently returning nothing. Reads no tasks file, so its answer depends on `roadmap.json` alone and stays fixed while a concurrent `/aimi:execute` rewrites tasks files; ordered by numeric id. Ungated by `_roadmap_require_contracts` for the same reason the five lifecycle verbs are: it reads no `creates`/`needs` entry.
- **`roadmap-set-status --feature <slug> --phase <id> --status <status> [--force]`** — Transitions a phase's lifecycle status (`pending → planned → in_progress → completed`, or `→ verification_failed`, or `→ cancelled`). `--force` overrides the *transition-order* check only. It never overrides any of the three hard preconditions on reaching `completed`, all of which run even with `--force`: `roadmap-write-handoff` must already have written that phase's `handoff.md` to disk; a phase that owes a visual comparison (per `_visual_gate_requirement`, the one predicate behind `roadmap-visual-gate-required`) must carry a `phase.visualGate.status` of `passed`, `skipped` or `accepted`, recorded with `roadmap-record-visual-gate` — an unrecorded gate and a recorded `diverges` both refuse, with distinct wording, and an unreadable tasks shape degrades to the same advisory the story-level check gives rather than a refusal; and **every member of the phase's own tasks file(s)** must carry no unjudged verification — no story whose `verification.status` is the literal `pending` (issue #135), and no `metadata.smellWarnings` entry of type `verify-coverage` without an `acknowledged: true` beside it. A fourth precondition, `acknowledge-evidence`'s gate (below), refuses a phase whose completed stories carry no proven `verification.evidence.discriminating`, unless a non-lapsed `metadata.evidenceAcknowledged` is present. `skipped`, `passed` and `failed` all pass as verification statuses: they record that somebody looked. **Both predicates ask only about stories whose own `status` is `completed`** — a verification judges work that was done. That scope is load-bearing rather than a softening: `cascade-skip` writes `status: "skipped"` and never touches `verification.status`, so without it any phase carrying one failed story could never be closed at all. Note the two different `skipped` in play — a STORY's status and a story's VERIFICATION status are separate fields, and only the second is a judgment. **"Member(s)" is plural on purpose, since US-006:** an un-split phase has exactly one — `<feature>-phase-<id>-tasks.json`, via `_phase_tasks_path` — but a SPLIT phase's stories live in more than one file, resolved by `_completed_gate_resolve_members` the same main-file-first, then marker-anchor-plus-siblings, then legacy-frontend/backend-pair, then empty discipline `cmd_split_detect` uses to find its own candidate pool (see the drift-note comment beside it in `roadmap.py`, and `TERMINAL_STORY_STATUSES`' own comment naming the earlier three copies of that discipline). Every resolved member is judged, and a refusal line names its own member's path — never the phase's single absent main file, which is what let a split phase's unjudged verification hide in a sibling file the gate never opened before this. The tasks-file check measures rather than assumes, and now says so on any member it could not read: a member that resolves but will not parse, or an empty resolved-member list, draws exactly one `Advisory: roadmap-set-status: phase <id> completed-gate could not judge ...` line on stderr — degrading AUDIBLY rather than passing in silence — and still never refuses the transition on that member alone.
  - **`cancelled` is the other terminal status, for a phase abandoned rather than finished.** `pending`/`planned` → `cancelled` needs no `--force`; `in_progress`/`verification_failed` → `cancelled` need it, the same as any other out-of-order transition. `completed` → `cancelled` is refused even with `--force` — a completed phase's `creates` were already delivered, and this transition has no override, the same non-forceable shape as the `handoff.md` precondition above. `cancelled` → `pending` (reopening) is refused without `--force` and succeeds with it; `cancelled` → `cancelled` is an idempotent success; every other departure from `cancelled` — including `verification_failed`, otherwise reachable from any status without `--force` — is refused even with `--force`. Reaching `cancelled` clears the phase's claim in the same locked write, the same as reaching `completed`. A cancelled dependency satisfies a downstream phase's `dependsOn` the same way a completed one does, and a cancelled phase is never claimable — not by `roadmap-claim`'s auto-selection, and not via an explicit `--phase` override.
- **`roadmap-claim --feature <slug> --session-id <id> --session-pid <pid> [--phase <id>]`** — Atomically claims the next eligible phase (or a specific `--phase` override) for a session via a locked check-and-set. Auto-releases stale claims whose `claimedPid` is no longer alive before choosing. Idempotent: re-claiming a phase the same session already owns returns it again instead of erroring.
- **`roadmap-release-claim --feature <slug> --phase <id>`** — Manual escape hatch to release a phase's claim (in addition to automatic stale-claim recovery).
- **`roadmap-reconcile --feature <slug>`** — Reconciles every phase's `status` against its own `<feature>-phase-<id>-tasks.json` ground truth (derived from that file's story statuses) and applies corrections in place. A correction that would set a phase to `completed` is applied only when `handoff.md` already exists on disk for that phase; otherwise it is reported as `blocked` rather than applied. Applying a `completed` correction also clears that phase's claim in the same write — reconcile does not otherwise touch claims. **A phase whose stored status is `cancelled` is skipped entirely, on the status check alone, before its tasks file is ever read** — it never appears in `corrections` or `blocked`, and stays `cancelled` on disk whatever its ground truth would read, since cancelled is abandoned by choice rather than by whatever state its stories happen to be in. Returns `{corrections, blocked}`.
- **`roadmap-write-handoff --feature <slug> --phase <id> [--file <path>]`** — Writes `phase-N/handoff.md` from a structured payload (`decisions`, `artifacts`, `deviations`, `deferred`, `contracts` arrays). A precondition for `roadmap-set-status ... --status completed`.
- **`roadmap-record-visual-gate --feature <slug> --phase <id> --status <passed|diverges|skipped|accepted> [--reason <text>] [--review <path>]`** — Locked write of a phase's visual-gate verdict into `roadmap.json` as `phases[].visualGate = {status, reason, review, recordedAt}` (`reason`/`review` are `null` when not given, `recordedAt` is an ISO-8601 UTC time). One crossing inside the lock, `roadmap-set-status`'s shape. `--status` outside the four values is refused naming all four; `diverges`, `skipped` and `accepted` require a non-blank `--reason` (refused naming `--reason`, in that order, before the document is read), `passed` does not. `--review` is confined by `validate_path_in_project` before the lock is taken. It always replaces the whole `visualGate` object, with no read-old-merge-new step, so a resumed or re-verified phase carries exactly one record. A phase id absent from `roadmap.json` is refused, naming the id and the roadmap path. Ungated by `_roadmap_require_contracts` — it touches no `creates`/`needs` entry.
- **`roadmap-visual-gate-required --feature <slug> --phase <id>`** — Read-only, no lock. Derives from the phase's own tasks file(s) whether a visual comparison is owed and prints `{required, reason, prototypePaths, designSpec, visualStories, groups}`: `required` is true only when `metadata.prototypePaths` is non-empty AND at least one **completed** story carries `verification.strategy == "visual"` — never either alone — and `reason` names which of the outcomes fired with its counts. `visualStories` is `[{id, url}]` and `groups` the number of resolved tasks files, aggregated across every member of a split phase through `_completed_gate_resolve_members` and `_completed_story_ids`, the same helpers the completed gate uses. The predicate is its own function, `_visual_gate_requirement`, so a completed-phase gate can call the same rule rather than restate it. `metadata.designBundle` carries no prototype list of its own, so the bundle case is the same `prototypePaths` signal. An unreadable member draws the completed gate's audible advisory and contributes nothing.
- **`validate-contracts <feature> [--phase <id>] [--agent-mode]`** — Checks a phase's declared `creates`/`needs` contracts for duplicates and suspicious content; `--agent-mode` demotes hard blocks to warnings (mirrors the Phase 3.1/4.1 `--agent-mode` convention). Reads `roadmap.json` and `handoff.md` only, and never inspects source code — that is `verify-creates`' job. Its duplicate-creates scan excludes a cancelled phase's own `creates` (see `roadmap-amend-phase` below — both call the same `duplicate_creates()`). **A cancelled phase never satisfies a scoped (`--phase`) needs check either**, even when a dependent's `dependsOn` already lists it: `SATISFIED_DEPENDENCY_STATUSES` treats the dependency EDGE as satisfied, but the scoped delivery gate asks a different question — was the need actually DELIVERED — and `prov_status == "completed"` is false for `"cancelled"` the same as for any other non-completed status, so the need reports `not-delivered` with no code change needed for that path.
- **`verify-creates --feature <slug> --phase <id> [--dir <container-path>]`** — Proves a phase's declared `creates[]` artifacts actually exist in code, by searching the files git tracks in `--dir` (the phase container; defaults to the project root). Reads each entry's own `identity` field and runs the same steps against every one, whatever kind it names — the search itself is documented once, in `commands/references/scope-contexts.md` § *What verification looks for*. Prints one verdict object per entry (`{identity, status, method, evidence, gitStatus}`); it is a query rather than a gate, so producing a verdict array exits 0 even when every entry is `missing`. `/aimi:execute` calls it once per participating repository at phase close and unions the verdicts.
- **`phase-overlap <feature> <phase-a> <phase-b>`** — Compares two expanded phases' task files' `implementation.files` sets and emits `{overlapping_files: [...]}`. It reports the overlap only — no splitting suggestion; the caller decides what to do with it.
- **`roadmap-sweep <feature>`** — Batch contract/status consistency sweep across an entire roadmap. A cancelled phase's own `creates` never appear in `orphanCreates` and its own `needs` never appear in `deferredNeeds` — those two OUTPUT arrays drop a cancelled phase's own reported entries — but the `needed`/`providers` reference sets every OTHER phase's verdict is computed against are left unfiltered, since the exclusion scopes to a cancelled phase's own entries only: a live phase's create consumed only by a cancelled phase's need is still not an orphan, and a live phase's need whose only provider is a cancelled phase is still deferred.
- **`estimate-payload --outline <path> [--research <path>]... [--spec <path>]... [--prototype <path>]... [--budget-bytes <n>] [--budget-fraction <0-1>]`** — Advisory token/byte budget estimate for an outline plus its cited sources; used to warn before a phase's expansion payload gets too large, suggesting a split along a semantic seam.

## Roadmap File Schema

> `roadmap.json` lives at `.aimi/tasks/<feature>/roadmap.json` and tracks phase/milestone lifecycle state for large-scope features. Key fields: `roadmapVersion` ("2.0"), `feature` (slug), `createdAt` (ISO 8601), `brainstormPath` (optional), `integrationBranch` (optional — the feature-level branch the roadmap's first phase should PR against; see `roadmap-init`'s `--integration-branch`), `phases[]{id(number),name,goal,slug,dir,status(pending|planned|in_progress|completed|verification_failed|cancelled),dependsOn[](phase ids),branch(optional),notes(optional),successCriteria[](optional),creates[](optional),needs[](optional),areas[](optional),claim(null|{claimedBy,claimedAt,claimedPid})}`. `integrationBranch` is additive-optional: absent on any roadmap.json written before it existed, and its absence is never an error — no migration reads or writes it. `cancelled` is a terminal status alongside `completed` — see `roadmap-set-status`'s `cancelled` bullet above for its transition graph, claim-release, and dependency-satisfaction treatment.
> `creates[]` and `needs[]` hold `{identity, description}` objects — exactly those two keys, `description` `""` rather than `null` when absent. `roadmapVersion` tracks that entry shape and nothing else: `"1.0"` meant one string, `"identity (description)"`. Every contract-READING verb refuses a pre-`2.0` document by name and points at `normalize-contracts`; the five lifecycle verbs (`roadmap-get`, `roadmap-set-status`, `roadmap-claim`, `roadmap-release-claim`, `roadmap-reconcile`) read one unchanged, so a migration never strands a session already in flight.
> `phases[].dir` is a single-path-component directory name matching `^phase-[0-9]+(\.[0-9]+)?(-[a-z0-9][a-z0-9-]*)?$` (e.g. `phase-2`, `phase-2.1-auth-refactor`) — never a slash or `..`.
> `phases[].claim` is written only by `roadmap-claim` and cleared by `roadmap-release-claim`, or automatically when `claimedPid` is no longer alive (PID-liveness check mirrors the guard-runtime-state `_is_alive` pattern).
> All free-text phase fields (`name`, `goal`, `notes`, `successCriteria[]`, `branch`, `brainstormPath`) are sanitized before write using the same regime as `commands/references/sanitization.md` (strip newlines/backticks/`$(`, truncate).

## Tasks File Schema

> Key fields: `schemaVersion` ("3.3"), `metadata{title,type,branchName,createdAt,baseRef(optional),pluginVersion(optional),finalize(optional:{intent,files[],commitSubject}),planPath,roadmapPath(optional),brainstormPath(optional),researchDepth,maxConcurrency,researchPaths[](optional),prototypePaths[](optional),prototypeSuperseded[](optional:{path,decision,note}),issues[](optional),frontendOnly(optional),execution(optional:"container"|"inline", default "inline" when absent — see `commands/references/execution-mode.md` for the read contract; `/aimi:plan` writes `"container"` by default for freshly generated flat files),backendSpec(optional:{endpoints[],dataModels[],businessRules[],businessContext{summary,userRoles[],constraints[],assumptions[],successCriteria[]}}),splitGroup(optional:{project,index,total,siblings[],after[](optional)}),designBundle(optional:{root,readme,chats[],businessSpec,designSpec}),designTokens(optional),decisions[](optional:{anchor,source,text,resolution}),evidenceAcknowledged(optional:{reason,acknowledgedAt,completed} — written only by `acknowledge-evidence`; see its section)}`, `userStories[]{id(US-NNN),title,description,acceptanceCriteria,status,dependsOn,project,wave,tasks[](optional,max50,each≤5000chars),implementation{files,outputs(optional),approach,verify},verification{strategy,status,url,expect,evidence(optional)},gate{type,status,prompt,options}}`
> The `project` field is optional on stories — when present, it specifies the relative path from AIMI_ROOT to the target git repository for multi-repo execution.
> `implementation.files` holds in-repository paths only: relative to the story's own repository, committed by the story. `implementation.outputs` is the optional companion for what a story produces OUTSIDE the repository: a list of paths relative to the AIMI root, each starting with `.aimi/` followed by a path. The executor creates each one itself (`mkdir -p` its parent under `"$AIMI_ROOT"`), never stages or commits it, and never treats it as a commit-verification target. Both lists are judged by the one lexical path rule, `implementation_path_problem` in `tasks.py` (no filesystem access): a non-string, an empty or whitespace-only entry, an absolute path, a `~`-led path, a `..` segment, any whitespace, a backslash or a `.` segment is refused, and an `outputs` entry must also carry the `.aimi/` prefix; a trailing slash (a directory entry) is allowed. Absent and `null` are both fine for `outputs`.
> Rule **R24** of `validate-tasks` covers `implementation.outputs`: when the key is present and not null it must be a list of strings that each pass the path rule, and a malformed one is an ERROR, one finding per bad entry (or a single finding about the field when it is not a list of strings). It is checked in `validate_tasks` after R23 and skipped when the key is absent, so a tasks file without it validates byte for byte as before. Rule **R17** stays a warning: a `files` entry that leaves the repository (absolute, `~`-led or with a `..` segment) now draws its own warning, `implementation.files leaves the story's repository: <entries> — move a file outside the repository to implementation.outputs`, and is never also reported as a directory that does not exist. `validate-staging` and the `story-merge` refusal hold `files` to the whole path rule, not only to the escape half R17 warns about.
> The verify environment is documented here once. The executor exports `TASKS_FILE_PATH` and `AIMI_ROOT` into the environment of both runs of a story's `implementation.verify` (the step 1.5 pre-run and the step 4 verify), `AIMI_ROOT` being the value `/aimi:execute` handed it in the task pointer and never re-derived, because a worktree has no `.aimi/` of its own; a verify can read `"$AIMI_ROOT/.aimi/..."` with no relative hop. `verify-probe` and `probe-plan` export the same `AIMI_ROOT` to every segment they run: `aimi-cli.sh` derives it as `AIMI_DIR` minus its trailing `/.aimi` (not `PROJECT_ROOT`, which is the git toplevel and differs from it in a multi-repo layout) and hands it to `tasks.py` as `--aimi-root <absolute dir>`, which overwrites any stale value in the environment for the duration of the probe and restores the previous one afterwards. A relative `--aimi-root` is refused, and a call without the flag leaves the environment as it found it.
> `metadata.splitGroup` is an optional object written by `story-merge` on the **PROJECT axis only** (`--split full-stack` over 2 or more distinct `.project` values): `{project, index, total, siblings[], after[]?}` — the file's own project routing key (`"."` for the root group), its 1-based position in the returned file list, the total file count, the paths of the other N−1 files, and optionally `after[]`, the subset of those paths this file must follow (ordering only; the SIDE axis never carries it). `/aimi:plan` Phase 4 preserves it verbatim when patching `metadata`, and `/aimi:execute` Step 0.9 reads `metadata.splitGroup.project` to root each split's worktree/container at that project's own repo — losing it reintroduces `fatal: not a git repository` in multi-repo layouts. Phase mode reads the same field for the same purpose, not only the flat Step 0.9 flow: `/aimi:execute`'s **Detect a Full-Stack Split Inside This Phase** (`commands/references/execute/step-1-7-detect-split.md`) and **Create Phase Containers Per Project Group** (`commands/references/execute/step-1-7-per-group-containers.md`) resolve a claimed phase's own per-repository phase container and phase branch from `metadata.splitGroup.project` on a split phase's member files, or from a story's own `project` field on a single non-split phase tasks file — one repository at a time, same as the flat flow. SIDE-axis, legacy, and frontend-only files have no `splitGroup` key and none should be invented for them.
> `metadata.smellWarnings` is an optional array written by `story-merge`; absent entirely when no smell is detected. Each entry is discriminated by `type`:
> - `{type: "orphan-symbol", storyId, symbols[], message}` — Phase 4.2: a story introduces a named symbol no sibling story references.
> - `{type: "verify-coverage", storyId, commands[], message, acknowledged(optional), acknowledgedReason(optional), acknowledgedAt(optional)}` — Phase 4.3: a story's acceptance criteria assert a command its own `implementation.verify` never runs. The three `acknowledged*` keys are the only ones here `story-merge` does not write: they are added by `aimi-cli.sh acknowledge-smell` (see its entry under Story Lifecycle Subcommands; a re-merge regenerates the array and resets them), and `roadmap-set-status --status completed` refuses the phase until every `verify-coverage` entry carries it as the JSON literal `true` (issue #135). Only that literal counts — the string `"true"` and the number `1` both leave the entry unacknowledged, because an acknowledgement that can be produced by accident acknowledges nothing.
> - `{type: "field-overlap", storyId, ratio, ngram, message}` — advisory, written by `story-merge`: the share of a story's `tasks[]` word `ngram`-grams (4) that also occur in its `implementation.approach` reached the threshold. Never acknowledged by anything that gates; see `### Advisory smells`.
> - `{type: "story-oversize", storyId, bytes, medianBytes, floorBytes, message}` — advisory, written by `story-merge`: the story serializes to more than `floorBytes` (12288), or to more than twice the plan median. Same status as `field-overlap`.
> - `{type: "audit-duplication", storyId, ratio, ngram, message}` — advisory, written by `story-merge`: an audit patch changed both `tasks` and `implementation.approach` (per `changedFields` in `audit-result.json`) and the `ngram`-gram overlap of `tasks[]` with the approach reached `AUDIT_DUPLICATION_THRESHOLD` (0.20). Same shape as `field-overlap`, different trigger.
> - `{type: "stale-sibling-note", storyId, cited[], message}` — advisory, written by `story-merge`: an older `notes` paragraph (one before the last `NOTES_SEPARATOR`) cites another story of the plan; `cited` is the sorted `US-NNN` ids.
> - `{type: "leftover-outline-token", storyId, fields[], message}` — advisory, written by `story-merge`: an `outline:` plus digits survived the remap in a field other than `dependsOn`; `fields` is the sorted field paths.
> - `{type: "ac-test-enumeration", storyId, index, count, message}` — advisory, written by `story-merge`: `acceptanceCriteria[index]` names `count` (3 or more) distinct `test_*` identifiers. One entry per criterion, so a story can carry several.
> - `{type: "cross-file-dep-dropped", storyId, side, becameRoot, droppedDeps: [{id, side, title}], message}` — **SIDE axis**, written by `_story_merge_write_split` when `--split full-stack` drops a `dependsOn` edge across the frontend/backend boundary. `side` is `"frontend"`/`"backend"` (`"unknown"` for an unresolvable target).
> - `{type: "cross-file-dep-dropped", storyId, project, becameRoot, droppedDeps: [{id, project, title, foundationEdge}], message}` — **PROJECT axis**, written by `_story_merge_write_project_split` when `--split full-stack` drops a `dependsOn` edge across a repo boundary. `project` is the owning group's routing key (e.g. `"apps/web"`, `"."` for the root group; `"unknown"` for an unresolvable target). `foundationEdge` is `true` exactly when the dropped edge's pre-remap target is a story `--foundation` named, in **any** project group. It can never mark a merge-injected edge: injection is per group, so both endpoints of an injected edge share one `group_key` and therefore one per-block idmap, and the remap never drops it. Every `true` reading is consequently a **hand-authored** dependency reaching into another group's foundation — one repository's Foundation Gate resolved Accept while a sibling's resolved Skip, or a story predating the per-repo split — worth flagging apart from an ordinary cross-project drop because of what it targets, not because of where it came from. It carries one stderr note line separate from the ordinary drop-count banner. `false` otherwise, and on every entry of a run without `--foundation`.
>
> `side` and `project` are mutually exclusive per entry — the axis decides which one is emitted, and consumers (e.g. the `/aimi:plan` Step 5 renderer) read whichever is present. `becameRoot` is `true` when the drop emptied the story's entire `dependsOn` list, making it a false wave-1 root. The combined array is written identically into every file the split produces (both side files, or all N project files). `message` and `droppedDeps[].title` embed sub-agent-authored titles already passed through `_rm_sanitize` (200-char cap) before write.
> `metadata.decisions[].anchor` valid forms: `specFlow:<key>`, `outline:edit:<idx>` (zero-padded index into the outline list, e.g. `outline:edit:02`), `phase:edit:<idx>` (zero-padded index into a proposed `phases` array at edit time, e.g. `phase:edit:02` — distinct from the persisted numeric phase `id`; used by both the `/aimi:brainstorm` roadmap-gate and the `/aimi:plan` inline fallback gate, see `source` below for how to tell them apart), `foundation:<topicSlug>` (the topic slug used to name the accepted/adjusted/skipped proposal file, e.g. `foundation:userAuth` — recorded by the `/aimi:plan` Phase 1.9 Greenfield Foundation Gate for the single-repo `.` foundation root, which is the only form a single-repo run writes), `foundation:<topicSlug>:<repoSlug>` (the same form with a trailing repository discriminator, e.g. `foundation:userAuth:api` — recorded by the same gate for every non-`.` foundation root of a multi-repo layout, one entry per root, where `<repoSlug>` is that root's validated child-repo directory name), `removeStory:<id>` (the removed story's own id, e.g. `removeStory:US-006` — the one anchor form written by `aimi-cli.sh`'s `remove-story` verb rather than by a command at plan time; see the `remove-story` entry under `aimi-cli.sh Story Lifecycle Subcommands` above). `metadata.decisions[].source` valid values: `"specFlow:CriticalQ<n>"`, `"specFlow:Gap<n>"`, `"researchConflict"` (Phase 1.6b conflict escalation gate; anchor `researchConflict:<n>`), `"outline"` (for outline-gate edits recorded during the `/aimi:plan` outline gate), `"phaseGate"` (for roadmap-gate edits recorded in `phaseEditDecisions[]` during the `/aimi:brainstorm` Phase 3.5 roadmap definition gate; never written to a tasks.json `metadata.decisions[]` array), `"phase"` (for phase-cut Edit-round edits recorded in `oqDecisions[]`, and thus flushed to `metadata.decisions[]`, by the `/aimi:plan` Phase 0 Scope-Context Classification (Inline Fallback) gate — the no-brainstorm/legacy-brainstorm path that classifies scope contexts directly instead of reusing a brainstorm's `phases:` frontmatter), `"foundation"` (for the Aceitar/Ajustar/Pular decisions of the `/aimi:plan` Phase 1.9 Greenfield Foundation Gate, recorded in `oqDecisions[]` with anchor `foundation:<topicSlug>` and thus flushed to `metadata.decisions[]`), `"removeStory"` (the sole writer of anchor `removeStory:<id>` above — the one source value this schema documents that a `tasks.py` op writes directly, at execution time, rather than one a command assembles into `oqDecisions[]`/`phaseEditDecisions[]` first).
> `foundationProposalPath` is a `.aimi/brainstorms/*.md` frontmatter key, not a `tasks.json` field — a single relative-path string (never a list, unlike `researchPaths`, since one repository has at most one active foundation proposal), emitted only when `/aimi:brainstorm`'s Phase 3.7 (Foundation Synthesis) writes and validates its 4-section artifact (fresh reuse counts as validated too); omitted entirely — no placeholder value, no companion boolean flag — when Phase 3.7 did not fire or its validation gate failed. `/aimi:plan`'s Phase 0 reads this key under the same strict path-confinement regime as its `### Prototype Context` subsection (absolute resolve, `AIMI_ROOT` prefix check, reject traversal/symlinks — not the looser `researchPaths` join-and-exists check), requires the target file to exist and be no older than 14 days, and on success populates the working-memory `foundationProposalPath` variable that Phase 1.9's Greenfield Foundation Gate consumes as a second reuse source (alongside its own topicSlug glob) for its fire-condition and reuse-source resolution.
> `metadata.prototypeDropped` is an optional array with **two writers**, and the two disagree about whether the prototype was read at all. Phase 0 § Prototype Context's aggregate prototype drop cap writes an entry, `reason: "aggregate-cap"`, for a prototype block the payload ceiling refused before the plan ever saw its contents — the plan was written from the filename alone. Phase 3d § Per-Entry View-Scoped Prototype Block Preparation's no-anchor degradation writes the other kind, `reason: "no-view-anchors"`, for a prototype that carries zero `data-view` sections and so is sent whole to the first outline entry instead of being sliced — that prototype WAS read, by the entry that received it and by any expander that follows the read-on-demand path to it; "dropped" there names the per-entry slicing this record's sibling entries got, not an absence of reading. Each element is `{path, reason, bytes}` and exactly those three keys: `path` the prototype's own path as a non-empty string, `reason` a non-empty string naming which of the two writers produced it (the set of reasons belongs to the writers, not to this schema, so no enum is enforced here), and `bytes` the size each writer already weighed, as a number — never the JSON literal `true`, which a naive integer check would accept. It follows the omitted-when-empty convention `baseRef`, `pluginVersion` and `issues` already have: written only when something was actually dropped, absent otherwise, never `[]` and never `{}`. `validate-tasks` enforces exactly that shape as rule **R21** and refuses an empty array with a message of its own, because `[]` is the mistake the convention exists to prevent; an absent key is skipped entirely and validates byte for byte as it did before the key existed, the way R18 skips an absent `metadata.finalize`. It is a RECORD, and its one consumer only reads it — a `prototypeDropped` path is never opened, moved, deleted or resolved against the filesystem. The key IS in `STORY_CONTEXT_METADATA_KEYS`, so it reaches every spawned story executor's `get-story-context` payload, where `skills/story-executor/SKILL.md` reads it to learn that a prototype a story's acceptance criteria depend on is gone, and is told at each place it reads the key never to open, stat or resolve that path. It is not in `archive-task`'s cleanup loop. It consequently still carries no path confinement: every confined sibling is confined because something acts on its path, and the executor acts on this entry's `reason`, never on its `path` — a consumer that did resolve the path would need confinement this field does not have.
> `metadata.prototypeSuperseded` is the optional array a later DECISION writes about a prototype that stays in `metadata.prototypePaths`. When a decision recorded in `oqDecisions[]` changes something a loaded prototype depicts, `/aimi:plan` Phase 4 (the only writer, reading `oqDecisions[]` alone) appends `{path, decision, note}`: `path` the prototype's `AIMI_ROOT`-relative path, `decision` that entry's `anchor`, `note` sanitized. The prototype is RECORDED as superseded, never regenerated. It follows `prototypeDropped`'s omitted-when-empty convention exactly (never `[]`, never `null`) and is copied to every file of a split. `validate-tasks` enforces it as rule **R22**, appended after R21: a non-array, an empty array, a non-object entry, a missing/empty/non-string `path`/`decision`/`note`, or an unknown key is an ERROR naming `metadata.prototypeSuperseded`; `path` goes through `confined_spec_path`, so an escaping path is refused. Unlike `prototypeDropped` it IS in `STORY_CONTEXT_METADATA_KEYS`, and `skills/story-executor/SKILL.md` (which now reads five keys) tells the executor to read the entry next to the prototype and not reproduce the superseded decision. It is deliberately NOT in `archive-task`'s cleanup tuple, the same choice `prototypeDropped` made: `path` always names an entry already in `metadata.prototypePaths`, which `archive-task` already confines and removes, so a second deletion route would only duplicate it.

## Performance Guidelines

1. **Pointer-only handoff** - Spawn prompts carry only the story id in a `task_pointer` block; each subagent fetches its own full context via `$AIMI_CLI get-story-context $STORY_ID` as its first action
   - Keeps the orchestrator's working memory slim across waves — no inlined story body, no inlined prototype HTML in the spawn prompt
   - Prototype files are read by the subagent itself using the Read tool when `metadata.prototypePaths` is non-empty or `story.implementation.prototypeAnchor` is set

2. **Use CLAUDE.md/AGENTS.md** - Project conventions inline or referenced
   - Small files (<2KB) are inlined in prompt
   - Larger files are referenced for agent to read

3. **Compact prompts** - First story in a session gets the full template (SKILL.md "Prompt Template"); subsequent stories get the condensed variant (SKILL.md "Compact Template") where static sections (`<project_guidelines>`, `<execution_flow>`, `<tools>`, `<on_failure>`, `<project_root_boundary>`) are condensed to one-line summaries — NOT omitted, since each agent has fresh context. Story-specific and context-varying sections remain in full
   - Reduces prompt size by collapsing static sections; actual savings depend on story content and have not been benchmarked

4. **Fresh context per story** - Each Task agent starts with clean context
   - No memory carryover between stories
   - Learnings persist via CLAUDE.md/AGENTS.md files

5. **Spawned agent output behavior** - See `AGENTS.md` for output compression, safety escapes, and context-adaptive verbosity rules
   - AGENTS.md defines the rules; this file references them (no duplication)
   - AGENTS.md is portable across tools (Claude Code, OpenCode) and is the single source of truth for spawned agent behavior

## Guard Bypass Envs

Hooks support per-guard bypass via environment variables. Set `<name>=off` (or unset to leave the guard active). Bypass is intentional escape hatch — use sparingly and document why.

| Env Var | Hook | Behavior when `off` |
|---|---|---|
| `AIMI_DEFAULT_BRANCH_GUARD` | pre-bash-dispatcher (default-branch handler) | Allows commits on protected branches (main/master/develop) |
| `AIMI_SHELL_TRUE_GUARD` | pre-bash-dispatcher (shell-true handler) | Allows commits with shell=True in staged Python files |
| `AIMI_WORKTREE_BUDGET_GUARD` | pre-bash-dispatcher (worktree-budget handler) | Allows git worktree add beyond metadata.maxConcurrency |
| `AIMI_RUNTIME_STATE_GUARD` | guard-runtime-state | Allows direct Write/Edit to .aimi/state/, .aimi/tasks during execution, roadmap.json, phase-*/handoff.md, and staged story files (`.aimi/.tasks-staging/<run>/NN-*.json`) |

> `AIMI_RUNTIME_STATE_GUARD` (`guard-runtime-state.py`) intercepts the Write/Edit tool path and blocks direct writes to `roadmap.json` and `phase-*/handoff.md` (see Roadmap File Schema above) the same way it blocks `.aimi/tasks/*-tasks.json`, pointing the caller at the `roadmap-*` aimi-cli.sh verbs instead. This coverage is Write/Edit-tool-only — the hook is registered on `matcher: Write|Edit` (`hooks/hooks.json`) and reads `tool_input.file_path`. A Bash command that writes either file directly (e.g. `jq ... > roadmap.json`) is **not** intercepted.
