# Tasks File Schema

Plugin development notes, moved out of `plugins/aimi-engineering/CLAUDE.md` so that file loads whole. Read this when you change the `tasks.json` shape, a field of it, or a validator over it.

## Tasks File Schema

> Key fields: `schemaVersion` ("3.3"), `metadata{title,type,branchName,createdAt,baseRef(optional),pluginVersion(optional),finalize(optional:{intent,files[],commitSubject}),planPath,roadmapPath(optional),brainstormPath(optional),researchDepth,maxConcurrency,researchPaths[](optional),prototypePaths[](optional),prototypeSuperseded[](optional:{path,decision,note}),issues[](optional),frontendOnly(optional),execution(optional:"container"|"inline", default "inline" when absent — see `commands/references/execution-mode.md` for the read contract; `/aimi:plan` writes `"container"` by default for freshly generated flat files),backendSpec(optional:{endpoints[],dataModels[],businessRules[],businessContext{summary,userRoles[],constraints[],assumptions[],successCriteria[]}}),splitGroup(optional:{project,index,total,siblings[],after[](optional)}),designBundle(optional:{root,readme,chats[],businessSpec,designSpec}),designTokens(optional),decisions[](optional:{anchor,source,text,resolution}),evidenceAcknowledged(optional:{reason,acknowledgedAt,completed} — written only by `acknowledge-evidence`; see `docs/dev/story-lifecycle.md` § `acknowledge-evidence`)}`, `userStories[]{id(US-NNN),title,description,acceptanceCriteria,status,dependsOn,project,wave,tasks[](optional,max50,each≤5000chars),implementation{files,outputs(optional),approach,verify},verification{strategy,status,url,expect,evidence(optional)},gate{type,status,prompt,options}}`
> The `project` field is optional on stories — when present, it specifies the relative path from AIMI_ROOT to the target git repository for multi-repo execution.
> `implementation.files` holds in-repository paths only: relative to the story's own repository, committed by the story. `implementation.outputs` is the optional companion for what a story produces OUTSIDE the repository: a list of paths relative to the AIMI root, each starting with `.aimi/` followed by a path. The executor creates each one itself (`mkdir -p` its parent under `"$AIMI_ROOT"`), never stages or commits it, and never treats it as a commit-verification target. Both lists are judged by the one lexical path rule, `implementation_path_problem` in `tasks.py` (no filesystem access): a non-string, an empty or whitespace-only entry, an absolute path, a `~`-led path, a `..` segment, any whitespace, a backslash or a `.` segment is refused, and an `outputs` entry must also carry the `.aimi/` prefix; a trailing slash (a directory entry) is allowed. Absent and `null` are both fine for `outputs`.
> Rule **R24** of `validate-tasks` covers `implementation.outputs`: when the key is present and not null it must be a list of strings that each pass the path rule, and a malformed one is an ERROR, one finding per bad entry (or a single finding about the field when it is not a list of strings). It is checked in `validate_tasks` after R23 and skipped when the key is absent, so a tasks file without it validates byte for byte as before. Rule **R17** stays a warning: a `files` entry that leaves the repository (absolute, `~`-led or with a `..` segment) now draws its own warning, `implementation.files leaves the story's repository: <entries> — move a file outside the repository to implementation.outputs`, and is never also reported as a directory that does not exist. `validate-staging` and the `story-merge` refusal hold `files` to the whole path rule, not only to the escape half R17 warns about.
> Rule **R26** of `validate-tasks` refuses an `outline:` followed by digits in any field of a story, an ERROR naming the story, the field and the token. `outline:NN` is a staging-only reference that `story-merge` rewrites to `US-NNN` in every text field its walk covers (`_rewrite_story_text`), so one that survived names nothing an executor can resolve. `story-merge` already refuses a two-digit token whose idx has no staged file; R26 catches what its remap leaves as text (`outline:7`, `outline:007`) and anything written into the file after the merge. `validate-staging` reports the malformed forms earlier, while the expander can still be re-spawned. `outline:edit:NN`, the decision anchor, never matches. The merge's advisory `leftover-outline-token` smell, `validate-staging` and R26 all read tokens through one walk, `story_merge.outline_tokens_in`, which `tasks.py` imports, so the three cannot disagree about what a leftover token is.
> The verify environment is documented here once. The executor exports `TASKS_FILE_PATH` and `AIMI_ROOT` into the environment of both runs of a story's `implementation.verify` (the step 1.5 pre-run and the step 4 verify), `AIMI_ROOT` being the value `/aimi:execute` handed it in the task pointer and never re-derived, because a worktree has no `.aimi/` of its own; a verify can read `"$AIMI_ROOT/.aimi/..."` with no relative hop. `verify-probe` and `probe-plan` export the same `AIMI_ROOT` to every segment they run: `aimi-cli.sh` derives it as `AIMI_DIR` minus its trailing `/.aimi` (not `PROJECT_ROOT`, which is the git toplevel and differs from it in a multi-repo layout) and hands it to `tasks.py` as `--aimi-root <absolute dir>`, which overwrites any stale value in the environment for the duration of the probe and restores the previous one afterwards. A relative `--aimi-root` is refused, and a call without the flag leaves the environment as it found it.
> `metadata.splitGroup` is an optional object written by `story-merge` on the **PROJECT axis only** (`--split full-stack` over 2 or more distinct `.project` values): `{project, index, total, siblings[], after[]?}` — the file's own project routing key (`"."` for the root group), its 1-based position in the returned file list, the total file count, the paths of the other N−1 files, and optionally `after[]`, the subset of those paths this file must follow (ordering only; the SIDE axis never carries it). `/aimi:plan` Phase 4 preserves it verbatim when patching `metadata`, and `/aimi:execute` Step 0.9 reads `metadata.splitGroup.project` to root each split's worktree/container at that project's own repo — losing it reintroduces `fatal: not a git repository` in multi-repo layouts. Phase mode reads the same field for the same purpose, not only the flat Step 0.9 flow: `/aimi:execute`'s **Detect a Full-Stack Split Inside This Phase** (`commands/references/execute/step-1-7-detect-split.md`) and **Create Phase Containers Per Project Group** (`commands/references/execute/step-1-7-per-group-containers.md`) resolve a claimed phase's own per-repository phase container and phase branch from `metadata.splitGroup.project` on a split phase's member files, or from a story's own `project` field on a single non-split phase tasks file — one repository at a time, same as the flat flow. SIDE-axis, legacy, and frontend-only files have no `splitGroup` key and none should be invented for them.
> `metadata.smellWarnings` is an optional array written by `story-merge`; absent entirely when no smell is detected. Each entry is discriminated by `type`:
> - `{type: "orphan-symbol", storyId, symbols[], message}` — Phase 4.2: a story introduces a named symbol no sibling story references.
> - `{type: "verify-coverage", storyId, commands[], message, acknowledged(optional), acknowledgedReason(optional), acknowledgedAt(optional)}` — Phase 4.3: a story's acceptance criteria assert a command its own `implementation.verify` never runs. The three `acknowledged*` keys are the only ones here `story-merge` does not write: they are added by `aimi-cli.sh acknowledge-smell` (see its entry under Story Lifecycle Subcommands; a re-merge regenerates the array and resets them), and `roadmap-set-status --status completed` refuses the phase until every `verify-coverage` entry carries it as the JSON literal `true` (issue #135). Only that literal counts — the string `"true"` and the number `1` both leave the entry unacknowledged, because an acknowledgement that can be produced by accident acknowledges nothing.
> - `{type: "field-overlap", storyId, ratio, ngram, message}` — advisory, written by `story-merge`: the share of a story's `tasks[]` word `ngram`-grams (4) that also occur in its `implementation.approach` reached the threshold. Never acknowledged by anything that gates; see `docs/dev/planning-verbs.md` § Advisory smells.
> - `{type: "story-oversize", storyId, bytes, medianBytes, floorBytes, message}` — advisory, written by `story-merge`: the story serializes to more than `floorBytes` (12288), or to more than twice the plan median. Same status as `field-overlap`.
> - `{type: "audit-duplication", storyId, ratio, ngram, message}` — advisory, written by `story-merge`: an audit patch changed both `tasks` and `implementation.approach` (per `changedFields` in `audit-result.json`) and the `ngram`-gram overlap of `tasks[]` with the approach reached `AUDIT_DUPLICATION_THRESHOLD` (0.20). Same shape as `field-overlap`, different trigger.
> - `{type: "stale-sibling-note", storyId, cited[], message}` — advisory, written by `story-merge`: an older `notes` paragraph (one before the last `NOTES_SEPARATOR`) cites another story of the plan; `cited` is the sorted `US-NNN` ids.
> - `{type: "leftover-outline-token", storyId, fields[], message}` — advisory, written by `story-merge`: an `outline:` plus digits survived the remap in a field other than `dependsOn`; `fields` is the sorted field paths.
> - `{type: "ac-test-enumeration", storyId, index, count, message}` — advisory, written by `story-merge`: `acceptanceCriteria[index]` names `count` (3 or more) distinct `test_*` identifiers. One entry per criterion, so a story can carry several.
> - `{type: "cross-file-dep-dropped", storyId, side, becameRoot, droppedDeps: [{id, side, title}], message}` — **SIDE axis**, written by `_story_merge_write_split` when `--split full-stack` drops a `dependsOn` edge across the frontend/backend boundary. `side` is `"frontend"`/`"backend"` (`"unknown"` for an unresolvable target).
> - `{type: "cross-file-dep-dropped", storyId, project, becameRoot, droppedDeps: [{id, project, title, foundationEdge}], message}` — **PROJECT axis**, written by `_story_merge_write_project_split` when `--split full-stack` drops a `dependsOn` edge across a repo boundary. `project` is the owning group's routing key (e.g. `"apps/web"`, `"."` for the root group; `"unknown"` for an unresolvable target). `foundationEdge` is `true` exactly when the dropped edge's pre-remap target is a story `--foundation` named, in **any** project group. It can never mark a merge-injected edge: injection is per group, so both endpoints of an injected edge share one `group_key` and therefore one per-block idmap, and the remap never drops it. Every `true` reading is consequently a **hand-authored** dependency reaching into another group's foundation — one repository's Foundation Gate resolved Accept while a sibling's resolved Skip, or a story predating the per-repo split — worth flagging apart from an ordinary cross-project drop because of what it targets, not because of where it came from. It carries one stderr note line separate from the ordinary drop-count banner. `false` otherwise, and on every entry of a run without `--foundation`.
>
> `side` and `project` are mutually exclusive per entry — the axis decides which one is emitted, and consumers (e.g. the `/aimi:plan` Step 5 renderer) read whichever is present. `becameRoot` is `true` when the drop emptied the story's entire `dependsOn` list, making it a false wave-1 root. The combined array is written identically into every file the split produces (both side files, or all N project files). `message` and `droppedDeps[].title` embed sub-agent-authored titles already passed through `_rm_sanitize` (200-char cap) before write.
> `metadata.decisions[].anchor` valid forms: `specFlow:<key>`, `outline:edit:<idx>` (zero-padded index into the outline list, e.g. `outline:edit:02`), `phase:edit:<idx>` (zero-padded index into a proposed `phases` array at edit time, e.g. `phase:edit:02` — distinct from the persisted numeric phase `id`; used by both the `/aimi:brainstorm` roadmap-gate and the `/aimi:plan` inline fallback gate, see `source` below for how to tell them apart), `foundation:<topicSlug>` (the topic slug used to name the accepted/adjusted/skipped proposal file, e.g. `foundation:userAuth` — recorded by the `/aimi:plan` Phase 1.9 Greenfield Foundation Gate for the single-repo `.` foundation root, which is the only form a single-repo run writes), `foundation:<topicSlug>:<repoSlug>` (the same form with a trailing repository discriminator, e.g. `foundation:userAuth:api` — recorded by the same gate for every non-`.` foundation root of a multi-repo layout, one entry per root, where `<repoSlug>` is that root's validated child-repo directory name), `removeStory:<id>` (the removed story's own id, e.g. `removeStory:US-006` — the one anchor form written by `aimi-cli.sh`'s `remove-story` verb rather than by a command at plan time; see `docs/dev/story-lifecycle.md` § `remove-story`). `metadata.decisions[].source` valid values: `"specFlow:CriticalQ<n>"`, `"specFlow:Gap<n>"`, `"researchConflict"` (Phase 1.6b conflict escalation gate; anchor `researchConflict:<n>`), `"outline"` (for outline-gate edits recorded during the `/aimi:plan` outline gate), `"phaseGate"` (for roadmap-gate edits recorded in `phaseEditDecisions[]` during the `/aimi:brainstorm` Phase 3.5 roadmap definition gate; never written to a tasks.json `metadata.decisions[]` array), `"phase"` (for phase-cut Edit-round edits recorded in `oqDecisions[]`, and thus flushed to `metadata.decisions[]`, by the `/aimi:plan` Phase 0 Scope-Context Classification (Inline Fallback) gate — the no-brainstorm/legacy-brainstorm path that classifies scope contexts directly instead of reusing a brainstorm's `phases:` frontmatter), `"foundation"` (for the Aceitar/Ajustar/Pular decisions of the `/aimi:plan` Phase 1.9 Greenfield Foundation Gate, recorded in `oqDecisions[]` with anchor `foundation:<topicSlug>` and thus flushed to `metadata.decisions[]`), `"removeStory"` (the sole writer of anchor `removeStory:<id>` above — the one source value this schema documents that a `tasks.py` op writes directly, at execution time, rather than one a command assembles into `oqDecisions[]`/`phaseEditDecisions[]` first).
> `foundationProposalPath` is a `.aimi/brainstorms/*.md` frontmatter key, not a `tasks.json` field — a single relative-path string (never a list, unlike `researchPaths`, since one repository has at most one active foundation proposal), emitted only when `/aimi:brainstorm`'s Phase 3.7 (Foundation Synthesis) writes and validates its 4-section artifact (fresh reuse counts as validated too); omitted entirely — no placeholder value, no companion boolean flag — when Phase 3.7 did not fire or its validation gate failed. `/aimi:plan`'s Phase 0 reads this key under the same strict path-confinement regime as its `### Prototype Context` subsection (absolute resolve, `AIMI_ROOT` prefix check, reject traversal/symlinks — not the looser `researchPaths` join-and-exists check), requires the target file to exist and be no older than 14 days, and on success populates the working-memory `foundationProposalPath` variable that Phase 1.9's Greenfield Foundation Gate consumes as a second reuse source (alongside its own topicSlug glob) for its fire-condition and reuse-source resolution.
> `metadata.prototypeDropped` is an optional array with **two writers**, and the two disagree about whether the prototype was read at all. Phase 0 § Prototype Context's aggregate prototype drop cap writes an entry, `reason: "aggregate-cap"`, for a prototype block the payload ceiling refused before the plan ever saw its contents — the plan was written from the filename alone. Phase 3d § Per-Entry View-Scoped Prototype Block Preparation's no-anchor degradation writes the other kind, `reason: "no-view-anchors"`, for a prototype that carries zero `data-view` sections and so is sent whole to the first outline entry instead of being sliced — that prototype WAS read, by the entry that received it and by any expander that follows the read-on-demand path to it; "dropped" there names the per-entry slicing this record's sibling entries got, not an absence of reading. Each element is `{path, reason, bytes}` and exactly those three keys: `path` the prototype's own path as a non-empty string, `reason` a non-empty string naming which of the two writers produced it (the set of reasons belongs to the writers, not to this schema, so no enum is enforced here), and `bytes` the size each writer already weighed, as a number — never the JSON literal `true`, which a naive integer check would accept. It follows the omitted-when-empty convention `baseRef`, `pluginVersion` and `issues` already have: written only when something was actually dropped, absent otherwise, never `[]` and never `{}`. `validate-tasks` enforces exactly that shape as rule **R21** and refuses an empty array with a message of its own, because `[]` is the mistake the convention exists to prevent; an absent key is skipped entirely and validates byte for byte as it did before the key existed, the way R18 skips an absent `metadata.finalize`. It is a RECORD, and its one consumer only reads it — a `prototypeDropped` path is never opened, moved, deleted or resolved against the filesystem. The key IS in `STORY_CONTEXT_METADATA_KEYS`, so it reaches every spawned story executor's `get-story-context` payload, where `skills/story-executor/SKILL.md` reads it to learn that a prototype a story's acceptance criteria depend on is gone, and is told at each place it reads the key never to open, stat or resolve that path. It is not in `archive-task`'s cleanup loop. It consequently still carries no path confinement: every confined sibling is confined because something acts on its path, and the executor acts on this entry's `reason`, never on its `path` — a consumer that did resolve the path would need confinement this field does not have.
> `metadata.prototypeSuperseded` is the optional array a later DECISION writes about a prototype that stays in `metadata.prototypePaths`. When a decision recorded in `oqDecisions[]` changes something a loaded prototype depicts, `/aimi:plan` Phase 4 (the only writer, reading `oqDecisions[]` alone) appends `{path, decision, note}`: `path` the prototype's `AIMI_ROOT`-relative path, `decision` that entry's `anchor`, `note` sanitized. The prototype is RECORDED as superseded, never regenerated. It follows `prototypeDropped`'s omitted-when-empty convention exactly (never `[]`, never `null`) and is copied to every file of a split. `validate-tasks` enforces it as rule **R22**, appended after R21: a non-array, an empty array, a non-object entry, a missing/empty/non-string `path`/`decision`/`note`, or an unknown key is an ERROR naming `metadata.prototypeSuperseded`; `path` goes through `confined_spec_path`, so an escaping path is refused. Unlike `prototypeDropped` it IS in `STORY_CONTEXT_METADATA_KEYS`, and `skills/story-executor/SKILL.md` (which now reads five keys) tells the executor to read the entry next to the prototype and not reproduce the superseded decision. It is deliberately NOT in `archive-task`'s cleanup tuple, the same choice `prototypeDropped` made: `path` always names an entry already in `metadata.prototypePaths`, which `archive-task` already confines and removes, so a second deletion route would only duplicate it.
