# Roadmap Verbs and Schema

Plugin development notes, moved out of `plugins/aimi-engineering/CLAUDE.md` so that file loads whole. Read this when you change a `roadmap-*` verb, `roadmap.py` or the `roadmap.json` shape.

## aimi-cli.sh Roadmap Lifecycle Subcommands

Seventeen CLI subcommands manage the phase/milestone roadmap layer for large-scope features (see `commands/references/scope-contexts.md` for when a feature qualifies for phases vs. the flat single-scope-context pipeline). All are internal — consumed by `/aimi:brainstorm`, `/aimi:plan`, `/aimi:execute`, and `/aimi:status`, not invoked by users directly.

**One verb outside this list reads `roadmap.json` too, and it is `list-archivable`.** It is a `tasks.json` verb — it decides which task files a feature has finished with — but a feature folder's phase files surface as a unit only when the feature's own `roadmap.json` marks every phase completed, so it opens one roadmap per feature folder it finds. That read is `roadmap.py`'s `list-archivable-phases --roadmap <path>` op: path-shaped like `op_roadmap_eligible` rather than slug-shaped like the wrapper `cmd_roadmap_eligible`, because `list-archivable` walks whatever roadmaps it discovers and has no feature slug to give. It follows `roadmap-eligible`'s general form — a verdict for **every** phase, `{id, status, terminal, stuck}`, plus `nonTerminalCount` and `stuckIds` (the stuck ids already joined into the exact `, `-separated string the warning prints, so bash never re-implements `(.id|tostring)`) — and adds `usable`, because a roadmap.json this verb cannot read is a normal outcome that INCLUDES the feature anyway, where `read_doc` would `die()`. `terminal` is `status in TERMINAL_PHASE_STATUSES` — `completed` and `cancelled` both count, reused from story 01's constant rather than re-literalled — so a feature whose only non-completed phase is cancelled is included exactly as one that finished cleanly, and `nonTerminalCount` excludes a cancelled phase the same way. It reads no tasks file (`list-archivable` has already read those itself) and it is **ungated by `_roadmap_require_contracts`**, for the same reason `roadmap-eligible` is: it touches only `.phases[].status`, never a `creates`/`needs` entry. It is not a CLI subcommand — nothing dispatches `list-archivable-phases`; it is the one op in `roadmap.py` reached from outside the `roadmap-*` family, which is why `_VERB_FOR_OP` names `list-archivable` as the verb its diagnostics should point at.

**`python3` is a runtime requirement for these verbs, not only a test-time one.** Sixteen of the seventeen shell out to `scripts/roadmap.py`, which owns `roadmap.json`'s document logic; each calls `check_python3()` first and fails with an install hint when it is absent. `estimate-payload` is the one roadmap verb that shells out to nothing and stays pure Bash + jq. **Outside this group the requirement is no longer narrow** — `story-merge` needs it, so does every `tasks.json` verb, including the per-story hot path `/aimi:execute` runs (`mark-*`, `list-ready`, `next-story`, `count-pending`, `get-story-context`), and so does the whole `models.json` surface, where `detect-models` refuses and the four readers degrade instead. Do not read this section as the boundary of the dependency; the normative statement, its full scope, which verbs degrade rather than refuse, and what it means for an OpenCode install are in the top-level `CLAUDE.md` § Testing, and stating it twice is how the two drifted before.

- **`roadmap-init --feature <slug> [--file <path>] [--sync] [--brainstorm-path <path>] [--integration-branch <name>]`** — Materializes `roadmap.json` from a phases array (stdin or `--file`). `--sync` merges additively into an existing roadmap instead of erroring on an existing file. A `creates`/`needs` entry is `{identity, description}`; one carrying any other key, or a malformed identity, is refused here at write time — the identity/description contract and its diagnostics are documented once, in `commands/references/scope-contexts.md` § Creates/Needs Contracts. Refuses a pre-`2.0` roadmap under `--sync`, naming `normalize-contracts`, rather than merging the two entry shapes into one document. `--integration-branch` declares the feature-level integration branch a rolling-wave roadmap's first phase should open its PR against (issue #87's direction 1). **No command passes it** — it is a human affordance, the same shape `roadmap-amend-phase` is for correcting a phase, and issue #87 direction 1 documents hand-editing `roadmap.json` as the supported route. `/aimi:plan` briefly parsed the value out of brainstorm frontmatter and threaded it here; nothing ever wrote that frontmatter key, and the parse interpolated LLM-authored text into an executed bash line, so it was removed rather than given a producer — validated against the same branch pattern `roadmap-amend-phase --branch` already enforces on a phase, in `init-validate` — i.e. before the lock and before `mkdir -p`, so a refusal creates no feature directory and no stale `.lock` (`init-write` re-checks it, two layers on purpose). It is read only when materializing a fresh `roadmap.json`; an additive `--sync` call preserves whatever value (if any) is already on disk and never overwrites it from this flag, since the field is meant to be addable to an existing roadmap by hand.
  - **Sanitize reporting (D10/D11):** every free-text field it sanitizes — `name` 200, `goal` 2000, `slug` 100, `notes` 5000, each `successCriteria` entry 2000, each `areas` entry 500, `branch` 200 — and each `creates`/`needs` entry's `description` (500) is classified by `sanitize.py`'s `rm_sanitize_report(value, maxlen)`, which calls `rm_sanitize` itself twice (unclamped, then at the cap) rather than re-deriving any of its regexes. A field the sanitizer actually rewrote or truncated draws one stderr warning line — naming the phase, the field, the list index when the field is a list entry, the change kind(s) (`rewritten`/`truncated`, both possible together) and before/after character counts, **never the field's own value, before or after** — and the result JSON's `sanitized[]` array carries the same per-field records, `{phase, field, index, changes[], before, after}`, empty when nothing changed. `--sync`'s anti-clobber applies here too: a phase left untouched reports nothing, the same as it adds nothing to `added`. Both channels are populated only once the write has landed, so a refused call reports nothing because nothing was written.
- **`roadmap-amend-phase --feature <slug> --phase <id> [--goal <text>] [--branch <name>] [--name <text>] [--slug <slug>] [--file <path>] [--retarget-needs "<old>=<new>"]...`** — Corrects an **existing** phase's contract in place, under the same `flock` + `mktemp`-then-`mv` discipline `roadmap-init` uses. This is the verb `guard-runtime-state.py` points at when it blocks a Write/Edit on `roadmap.json`; before it existed, that redirect named nothing. Amendable fields are `goal`, `successCriteria`, `creates`, `needs`, `areas`, `branch`, `name`, `slug` — supplied as scalar flags or as a JSON object on stdin/`--file` (stdin is read only when no scalar flag is given). The merge is **partial by key presence**: a key present replaces that field wholesale, a key absent leaves the stored value byte-for-byte unchanged, as do every other phase and the document metadata — except `dir`, which is never itself a patch key but is **recomputed** from `id` and the (possibly amended) `slug`, using the exact `phase-<id>[-<slug>]` formula `roadmap-init`'s own `init_sanitize` applies, whenever `name` or `slug` is amended.
  - **`branch` is amendable** because nothing else writes it for an existing phase: `roadmap-init` sets it once at creation and `--sync`'s anti-clobber guarantee never revisits it — which is exactly why a decimal phase's `null` branch could not be filled in. Amending it rewrites the roadmap field only; it does not move a worktree or git branch an `in_progress` phase already created.
  - **`status` and `claim` are not amendable** on the opposite ground: `roadmap-set-status` already owns status (transition graph plus the `handoff.md` precondition) and `roadmap-claim`/`roadmap-release-claim` already own claims (PID liveness, self-reclaim). A second writer would duplicate those guarantees, so both keys are rejected by name pointing at their owner. `id` and `dependsOn` are phase identity with no writer at all and are rejected by name too; `dir` is refused with its own distinct message naming `slug` as the way to change it, rather than folding into that generic phase-identity message.
  - **`name` and `slug` are amendable, and the one pair here whose amendment is gated on more than its own shape.** Renaming a phase's identity can move a directory and rewrite another document (its own tasks file), so amending either is refused — by name, before `roadmap.json` or any file on disk is touched — unless the phase's own `status` is `pending` or `planned`, its `claim` is `null`, and every story in its own phase tasks file (resolved via `_phase_tasks_path`, when that file exists) is still `pending`. When the guard passes and the amended `slug` changes the computed `dir`, the same locked call also: validates the new `dir` against `DIR_REGEX` and against a collision with another phase's stored `dir` or an existing filesystem path (refusing before anything moves or writes); moves `<feature_dir>/<old_dir>` to `<feature_dir>/<new_dir>` on disk when that directory exists; rewrites that phase's own tasks file's `metadata.phase.dir` to the new `dir`; and rewrites `metadata.branchName`'s own `-phase-<idSlug>-<oldSlug>` segment to the new slug when it was present (the token `commands/references/plan/phase-4-metadata-identity.md`'s `branchName` rule composes). A phase whose directory exists but carries no tasks file yet still moves cleanly, with no tasks-file rewrite attempted. If the `roadmap.json` write then fails — the directory and the tasks file's metadata having already changed — the same call moves the directory back and restores the tasks file's metadata to their exact pre-amend values before exiting non-zero, leaving the tree exactly as it was. The result JSON's `move` key is `{from, to}` when a directory was moved, `null` otherwise.
  - Amended values pass `roadmap-init`'s own gates (same sanitizer and caps, same `creates`/`needs` identity guard, same branch pattern). Dropping or renaming a `creates` identity a later phase cites in `needs` is **refused by default**; `--retarget-needs "<old identity>=<new identity>"` (repeatable) authorizes it, and the same locked write then replaces every matching downstream `needs` entry with the amended phase's new `creates` entry verbatim. Identity comparison is exact equality on the entry's own `identity` field, never substring containment. Refuses a pre-`2.0` roadmap, naming `normalize-contracts`. An amendment that would duplicate another phase's `creates` identity is refused (it would produce a roadmap `validate-contracts` rejects) — **except a cancelled phase's own `creates` are exempt from that collision scan**, the same exemption `duplicate_creates()` applies, so a live phase may reuse an identity a cancelled sibling abandoned; a completed phase whose `handoff.md` omits a newly introduced identity only draws a stderr advisory and still writes.
  - **Sanitize reporting** follows `roadmap-init`'s identical shape (see above), over the same caps for whichever of its amendable fields the call actually carries — `name` 200, `goal` 2000, `slug` 100, each `successCriteria` entry 2000, each `areas` entry 500, `branch` 200, each `creates`/`needs` entry's `description` 500. Every entry's `phase` is this call's own `--phase`, since one call amends exactly one phase. Result JSON is `{roadmap, phase, amended[], retargeted[], sanitized[], move}`.
- **`normalize-contracts --feature <slug>`** — Migrates a roadmap's stored `creates`/`needs` entries from the `roadmapVersion` `1.0` form — one string, `"identity (description)"` — to the `2.0` form `{identity, description}`, in place, under the same `flock` + `mktemp`-then-`mv` discipline every other roadmap writer uses. Each identity is computed by the **same function every reader used before the migration**, so no identity changes by a byte and no downstream `needs` is repointed; an entry with no `(` gets `description: ""` (never `null`), and an entry already in object form is left untouched, which is what makes a second run a no-op. It does not judge: a prose or whitespace-bearing identity the current writer would refuse migrates unchanged, and the reader reports it afterwards by name — repairing on the way past would silently change what a phase promises. One-way: an entry whose text after the first `(` does not end in `)` loses that unbalanced trailing paren from its description, which the identity half never sees. Prints `{roadmap, converted, roadmapVersion}`, where `converted` counts entries that were strings *before* the run.
- **`roadmap-get --feature <slug> [--phase <id>] [--next-eligible]`** — Reads a single phase, or the next eligible-to-claim phase, from `roadmap.json`.
- **`roadmap-eligible --feature <slug> [--statuses <a,b>]`** — Prints one JSON object naming **every** phase in roadmap order with a machine-readable verdict — `{id, name, status, claim, eligible, unmet[]}`, each `unmet` entry `{id, status}` — plus `eligible` (the ordered ids of the eligible ones) and `eligibleCount`, so one call serves both a list rendering and a by-id lookup. Structured fields only: no field carries a sentence, because user-facing wording follows the reader's own language (`commands/references/user-communication.md`) and the calling command composes it. **Zero eligible exits 0** with an empty list — unlike `roadmap-get --next-eligible`, which exits 1 — so a command substitution can tell "no phase ready" apart from a broken CLI. `--statuses` defaults to `pending,planned` and refuses an unknown name instead of silently returning nothing. Reads no tasks file, so its answer depends on `roadmap.json` alone and stays fixed while a concurrent `/aimi:execute` rewrites tasks files; ordered by numeric id. Ungated by `_roadmap_require_contracts` for the same reason the five lifecycle verbs are: it reads no `creates`/`needs` entry.
- **`roadmap-set-status --feature <slug> --phase <id> --status <status> [--force]`** — Transitions a phase's lifecycle status (`pending → planned → in_progress → completed`, or `→ verification_failed`, or `→ cancelled`). `--force` overrides the *transition-order* check only. It never overrides any of the three hard preconditions on reaching `completed`, all of which run even with `--force`: `roadmap-write-handoff` must already have written that phase's `handoff.md` to disk; a phase that owes a visual comparison (per `_visual_gate_requirement`, the one predicate behind `roadmap-visual-gate-required`) must carry a `phase.visualGate.status` of `passed`, `skipped` or `accepted`, recorded with `roadmap-record-visual-gate` — an unrecorded gate and a recorded `diverges` both refuse, with distinct wording, and an unreadable tasks shape degrades to the same advisory the story-level check gives rather than a refusal; and **every member of the phase's own tasks file(s)** must carry no unjudged verification — no story whose `verification.status` is the literal `pending` (issue #135), and no `metadata.smellWarnings` entry of type `verify-coverage` without an `acknowledged: true` beside it. A fourth precondition, `acknowledge-evidence`'s gate (`docs/dev/story-lifecycle.md` § `acknowledge-evidence`), refuses a phase whose completed stories carry no proven `verification.evidence.discriminating`, unless a non-lapsed `metadata.evidenceAcknowledged` is present. `skipped`, `passed` and `failed` all pass as verification statuses: they record that somebody looked. **Both predicates ask only about stories whose own `status` is `completed`** — a verification judges work that was done. That scope is load-bearing rather than a softening: `cascade-skip` writes `status: "skipped"` and never touches `verification.status`, so without it any phase carrying one failed story could never be closed at all. Note the two different `skipped` in play — a STORY's status and a story's VERIFICATION status are separate fields, and only the second is a judgment. **"Member(s)" is plural on purpose, since US-006:** an un-split phase has exactly one — `<feature>-phase-<id>-tasks.json`, via `_phase_tasks_path` — but a SPLIT phase's stories live in more than one file, resolved by `_completed_gate_resolve_members` the same main-file-first, then marker-anchor-plus-siblings, then legacy-frontend/backend-pair, then empty discipline `cmd_split_detect` uses to find its own candidate pool (see the drift-note comment beside it in `roadmap.py`, and `TERMINAL_STORY_STATUSES`' own comment naming the earlier three copies of that discipline). Every resolved member is judged, and a refusal line names its own member's path — never the phase's single absent main file, which is what let a split phase's unjudged verification hide in a sibling file the gate never opened before this. The tasks-file check measures rather than assumes, and now says so on any member it could not read: a member that resolves but will not parse, or an empty resolved-member list, draws exactly one `Advisory: roadmap-set-status: phase <id> completed-gate could not judge ...` line on stderr — degrading AUDIBLY rather than passing in silence — and still never refuses the transition on that member alone.
  - **`cancelled` is the other terminal status, for a phase abandoned rather than finished.** `pending`/`planned` → `cancelled` needs no `--force`; `in_progress`/`verification_failed` → `cancelled` need it, the same as any other out-of-order transition. `completed` → `cancelled` is refused even with `--force` — a completed phase's `creates` were already delivered, and this transition has no override, the same non-forceable shape as the `handoff.md` precondition above. `cancelled` → `pending` (reopening) is refused without `--force` and succeeds with it; `cancelled` → `cancelled` is an idempotent success; every other departure from `cancelled` — including `verification_failed`, otherwise reachable from any status without `--force` — is refused even with `--force`. Reaching `cancelled` clears the phase's claim in the same locked write, the same as reaching `completed`. A cancelled dependency satisfies a downstream phase's `dependsOn` the same way a completed one does, and a cancelled phase is never claimable — not by `roadmap-claim`'s auto-selection, and not via an explicit `--phase` override.
- **`roadmap-claim --feature <slug> --session-id <id> --session-pid <pid> [--phase <id>]`** — Atomically claims the next eligible phase (or a specific `--phase` override) for a session via a locked check-and-set. Auto-releases stale claims whose `claimedPid` is no longer alive before choosing. Idempotent: re-claiming a phase the same session already owns returns it again instead of erroring.
- **`roadmap-release-claim --feature <slug> --phase <id>`** — Manual escape hatch to release a phase's claim (in addition to automatic stale-claim recovery).
- **`roadmap-reconcile --feature <slug>`** — Reconciles every phase's `status` against its own `<feature>-phase-<id>-tasks.json` ground truth (derived from that file's story statuses) and applies corrections in place. A correction that would set a phase to `completed` is applied only when `handoff.md` already exists on disk for that phase; otherwise it is reported as `blocked` rather than applied. Applying a `completed` correction also clears that phase's claim in the same write — reconcile does not otherwise touch claims. **A phase whose stored status is `cancelled` is skipped entirely, on the status check alone, before its tasks file is ever read** — it never appears in `corrections` or `blocked`, and stays `cancelled` on disk whatever its ground truth would read, since cancelled is abandoned by choice rather than by whatever state its stories happen to be in. Returns `{corrections, blocked}`.
- **`roadmap-write-handoff --feature <slug> --phase <id> [--file <path>]`** — Writes `phase-N/handoff.md` from a structured payload (`decisions`, `artifacts`, `deviations`, `deferred`, `contracts` arrays). A precondition for `roadmap-set-status ... --status completed`.
- **`roadmap-record-visual-gate --feature <slug> --phase <id> --status <passed|diverges|skipped|accepted> [--reason <text>] [--review <path>]`** — Locked write of a phase's visual-gate verdict into `roadmap.json` as `phases[].visualGate = {status, reason, review, recordedAt}` (`reason`/`review` are `null` when not given, `recordedAt` is an ISO-8601 UTC time). One crossing inside the lock, `roadmap-set-status`'s shape. `--status` outside the four values is refused naming all four; `diverges`, `skipped` and `accepted` require a non-blank `--reason` (refused naming `--reason`, in that order, before the document is read), `passed` does not. `--review` is confined by `validate_path_in_project` before the lock is taken. It always replaces the whole `visualGate` object, with no read-old-merge-new step, so a resumed or re-verified phase carries exactly one record. A phase id absent from `roadmap.json` is refused, naming the id and the roadmap path. Ungated by `_roadmap_require_contracts` — it touches no `creates`/`needs` entry.
- **`roadmap-visual-gate-required --feature <slug> --phase <id>`** — Read-only, no lock. Derives from the phase's own tasks file(s) whether a visual comparison is owed and prints `{required, reason, prototypePaths, designSpec, visualStories, groups}`: `required` is true only when `metadata.prototypePaths` is non-empty AND at least one **completed** story carries `verification.strategy == "visual"` — never either alone — and `reason` names which of the outcomes fired with its counts. `visualStories` is `[{id, url}]` and `groups` the number of resolved tasks files, aggregated across every member of a split phase through `_completed_gate_resolve_members` and `_completed_story_ids`, the same helpers the completed gate uses. The predicate is its own function, `_visual_gate_requirement`, so a completed-phase gate can call the same rule rather than restate it. `metadata.designBundle` carries no prototype list of its own, so the bundle case is the same `prototypePaths` signal. An unreadable member draws the completed gate's audible advisory and contributes nothing.
- **`validate-contracts <feature> [--phase <id>] [--agent-mode]`** — Checks a phase's declared `creates`/`needs` contracts for duplicates and suspicious content; `--agent-mode` demotes hard blocks to warnings (mirrors the Phase 3.1/4.1 `--agent-mode` convention). Reads `roadmap.json` and `handoff.md` only, and never inspects source code — that is `verify-creates`' job. Its duplicate-creates scan excludes a cancelled phase's own `creates` (see `roadmap-amend-phase` below — both call the same `duplicate_creates()`). **A cancelled phase never satisfies a scoped (`--phase`) needs check either**, even when a dependent's `dependsOn` already lists it: `SATISFIED_DEPENDENCY_STATUSES` treats the dependency EDGE as satisfied, but the scoped delivery gate asks a different question — was the need actually DELIVERED — and `prov_status == "completed"` is false for `"cancelled"` the same as for any other non-completed status, so the need reports `not-delivered` with no code change needed for that path.
- **`verify-creates --feature <slug> --phase <id> [--dir <container-path>]`** — Proves a phase's declared `creates[]` artifacts actually exist in code, by searching the files git tracks in `--dir` (the phase container; defaults to the project root). Reads each entry's own `identity` field and runs the same steps against every one, whatever kind it names — the search itself is documented once, in `commands/references/scope-contexts.md` § *What verification looks for*. Prints one verdict object per entry (`{identity, status, method, evidence, gitStatus}`); it is a query rather than a gate, so producing a verdict array exits 0 even when every entry is `missing`. `/aimi:execute` calls it once per participating repository at phase close and unions the verdicts.
- **`phase-overlap <feature> <phase-a> <phase-b>`** — Compares two expanded phases' task files' `implementation.files` sets and emits `{overlapping_files: [...]}`. It reports the overlap only — no splitting suggestion; the caller decides what to do with it.
- **`roadmap-sweep <feature>`** — Batch contract/status consistency sweep across an entire roadmap. A cancelled phase's own `creates` never appear in `orphanCreates` and its own `needs` never appear in `deferredNeeds` — those two OUTPUT arrays drop a cancelled phase's own reported entries — but the `needed`/`providers` reference sets every OTHER phase's verdict is computed against are left unfiltered, since the exclusion scopes to a cancelled phase's own entries only: a live phase's create consumed only by a cancelled phase's need is still not an orphan, and a live phase's need whose only provider is a cancelled phase is still deferred.
- **`estimate-payload --outline <path> [--research <path>]... [--spec <path>]... [--prototype <path>]... [--budget-bytes <n>] [--budget-fraction <0-1>]`** — Advisory token/byte budget estimate for an outline plus its cited sources; used to warn before a phase's expansion payload gets too large, suggesting a split along a semantic seam.

## Roadmap File Schema

> `roadmap.json` lives at `.aimi/tasks/<feature>/roadmap.json` and tracks phase/milestone lifecycle state for large-scope features. Key fields: `roadmapVersion` ("2.0"), `feature` (slug), `createdAt` (ISO 8601), `brainstormPath` (optional), `integrationBranch` (optional — the feature-level branch the roadmap's first phase should PR against; see `roadmap-init`'s `--integration-branch`), `phases[]{id(number),name,goal,slug,dir,status(pending|planned|in_progress|completed|verification_failed|cancelled),dependsOn[](phase ids),branch(optional),notes(optional),successCriteria[](optional),creates[](optional),needs[](optional),areas[](optional),claim(null|{claimedBy,claimedAt,claimedPid})}`. `integrationBranch` is additive-optional: absent on any roadmap.json written before it existed, and its absence is never an error — no migration reads or writes it. `cancelled` is a terminal status alongside `completed` — see `roadmap-set-status`'s `cancelled` bullet above for its transition graph, claim-release, and dependency-satisfaction treatment.
> `creates[]` and `needs[]` hold `{identity, description}` objects — exactly those two keys, `description` `""` rather than `null` when absent. `roadmapVersion` tracks that entry shape and nothing else: `"1.0"` meant one string, `"identity (description)"`. Every contract-READING verb refuses a pre-`2.0` document by name and points at `normalize-contracts`; the five lifecycle verbs (`roadmap-get`, `roadmap-set-status`, `roadmap-claim`, `roadmap-release-claim`, `roadmap-reconcile`) read one unchanged, so a migration never strands a session already in flight.
> `phases[].dir` is a single-path-component directory name matching `^phase-[0-9]+(\.[0-9]+)?(-[a-z0-9][a-z0-9-]*)?$` (e.g. `phase-2`, `phase-2.1-auth-refactor`) — never a slash or `..`.
> `phases[].claim` is written only by `roadmap-claim` and cleared by `roadmap-release-claim`, or automatically when `claimedPid` is no longer alive (PID-liveness check mirrors the guard-runtime-state `_is_alive` pattern).
> All free-text phase fields (`name`, `goal`, `notes`, `successCriteria[]`, `branch`, `brainstormPath`) are sanitized before write using the same regime as `commands/references/sanitization.md` (strip newlines/backticks/`$(`, truncate).
